# Фаза 2D — план следующей итерации экспериментов RAG

## Контекст
Текущий лидер (Фаза 2C): Qwen3-Embedding-4B (int8, dim 2048, без промпта) + fixed_1024 (1024 символа, overlap 10%) + Vector+Rerank (bge-reranker-v2-m3, top_k=10).

Открытые вопросы:
- Даёт ли 8B с бóльшими dim/чанком прирост (в Фазе 2B 4B и 8B были неотличимы, p=0.59, но бóльшие dim/чанк не проверялись).
- Улучшает ли качество семантическая нарезка (по абзацам/заголовкам) вместо фиксированной по символам.
- Подтвердить latency реранкера на CPU (TEI) для прода.

## Принцип: разводим факторы
Не менять всё сразу. Сначала фиксируем лучшую стратегию чанкинга на текущей модели (4B), затем на победившем чанкинге проверяем 8B/dim. Иначе результат неинтерпретируем.

## Блок A — модель и размерность

Подготовка:
- Поднять `max_length` в `encode()` с 512 до 1024 (иначе чанк 2048 символов обрежется, сравнение размеров будет нечестным).
- Проверить место на Drive (8B + dim 4096 = крупные векторы).

Сетка (модель 8B, стратегия S2 Vector+Rerank):

| chunk_size (символы) | dim  |
|---|---|
| 1024 | 2048 |
| 1024 | 4096 |
| 2048 | 2048 |
| 2048 | 4096 |

Метрики: P@5, R@5, MRR, NDCG@5, Hit@5, MAP + per-question MRR (для каждой конфигурации).

Анализ: каждую конфигурацию сравнить с лидером (4B/1024/2048) через Wilcoxon на per-question MRR. Вывод: что даёт эффект — размер вектора, размер чанка, или ни то ни другое (как 4B vs 8B в 2B).

## Блок B — стратегия чанкинга (по абзацам/заголовкам)

Гипотеза (Игорь): нарезка по абзацам/заголовкам точнее передаёт смысл, чем слепая по символам. При крупных чанках желательно поглощать заголовок и объединять 2-3 мелких соседних абзаца.

Шаг 0 — проверить структуру исходников: markdown с заголовками или плоский текст из PDF. От этого зависит выбор сплиттера.

Кандидаты:
- LangChain `MarkdownHeaderTextSplitter` (strip_headers=False) — если есть markdown-разметка.
- Docling `HybridChunker` — split больших + merge мелких соседних с одним заголовком, поглощение заголовков по умолчанию. Основной кандидат под нормативку из PDF.
- (опц.) `chonkie` — семантический чанкинг, тоже умеет заголовки.

Шаги:
1. Прогнать 2-3 варианта нарезки на той же базе.
2. Диагностика: распределение длин чанков (символы/токены), доля чанков, обрезаемых по max_length, визуальная проверка границ.
3. Векторизация (sentence-transformers, модели с HF), те же 44 вопроса, те же метрики + per-question MRR.
4. Сравнить лучшую семантическую нарезку с fixed через Wilcoxon.

Замечание: у крупных чанков обратная сторона — эмбеддинг усредняет несколько тем, точность на узких вопросах падает. Семантическая нарезка может дать больше, чем просто увеличение fixed-размера.

## Блок C — прод

- TEI-реранк на CPU: замер latency на наших чанках (~300-400 токенов), top_k=10 батчем. Подтвердить ~100 мс (батч), а не ~800 мс (последовательно).
- Зафиксировать: Vector+Rerank (TEI/CPU) — основной семантический поиск; BM25 — сквозной полнотекстовый поиск по документам (точные формулировки, термины).

---

## Критерии и оговорки
- Основная метрика сравнения — MRR (per-question, Wilcoxon + поправка на множественные сравнения).
- "Незначимо" (p>0.05) = "не доказали разницу", а НЕ "доказали, что одинаково". На 44 вопросах мощность ограничена.
- Если прирост незначим — оставаться на более лёгкой конфигурации (4B / fixed / меньший dim).
- Если для прода качество критично — расширить бенчмарк (>44 вопросов).
