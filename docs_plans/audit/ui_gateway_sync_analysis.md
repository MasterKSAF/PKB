## 2. Вопросы к backend по Gateway

### 2.1. POST /chat/sessions — должен ли принимать и сохранять `project_id`?

**Контекст:**
- В `query_service_api.md` поле `project_id` есть в запросе `POST /chat/sessions` (опциональное, `bigint`).
- В свежем mock Gateway `CreateSessionRequest` поле `project_id` **не принимает**, поэтому UI отправляет его, но mock фактически не связывает сессию с проектом.

**Вопрос:**
> Реальный Gateway/Qeury Service должен сохранять `project_id` и возвращать его в `GET /chat/sessions`? Или проект привязывается только через отдельный вызов?

**Рекомендация:**
- Синхронизировать mock Gateway с документацией: либо убрать `project_id` из документации, либо добавить его в mock.

---

### 2.2. /chat/projects — реальные проекты или UI создаёт сам?

**Контекст:**
- Сейчас `GET /chat/projects` возвращает пустой список.
- Без seed/project data дерево проектов в UI показывает только fallback «Рабочие диалоги».

**Вопрос:**
> Будет ли Gateway/Query Service возвращать реальные проекты (например, из внешней системы планирования), или UI должен создавать их через `POST /chat/projects`?

---

### 2.3. Финальный контракт связи chat project → chat session

**Контекст:**
- UI умеет объединять ответы `GET /chat/projects` и `GET /chat/sessions` в дерево.
- Но связь зависит от того, как данные приходят от Gateway.

**Вопрос:**
> Какой финальный формат? Варианты:
> 1. Плоский список: `GET /chat/sessions` возвращает `project_id`, UI делает join самостоятельно.
> 2. Вложенный список: `GET /chat/projects` возвращает `sessions[]` внутри каждого проекта.
> 3. Гибрид: оба endpoint работают, но `GET /chat/sessions` добавляет `project_name` (чтобы не делать N+1 запросов).

**Рекомендация:**
- Если остаётся плоский список (вариант 1), добавить `project_name` в `GET /chat/sessions` для удобства UI.

---

### 2.4. Финальный формат POST /chat/feedback

**Контекст:**
- `query_service_api.md` описывает `rating: "positive" | "negative" | "neutral"` (строка).
- Свежий mock Gateway принимает числовой `rating` и возвращает 422 на строковый.
- UI сейчас оставлен на числовом варианте, потому что он работает с текущим mock.

**Вопрос:**
> Какой финальный формат? Строковый (как в документации) или числовой (как в mock)?

**Рекомендация:**
- Если строковый — обновить mock Gateway. Если числовой — обновить документацию.

---

### 2.5. GET /chat/history/export — должен отдавать рабочую ссылку на файл?

**Контекст:**
- Сейчас Gateway возвращает объект с `url`, но GET по этому URL возвращает 404.
- UI сделал локальный fallback (генерация CSV на клиенте).

**Вопрос:**
> Какой способ доставки файла выбираем?
> 1. Возвращать `url` + обеспечивать рабочий GET по этому URL (файловое хранилище / CDN).
> 2. Возвращать готовый blob/base64/stream прямо в ответе `200` (без промежуточного URL).

**Рекомендация:**
- Вариант 1 (url) — стандартный для async-экспорта. Нужно либо реализовать файловое хранилище, либо убрать `url` из контракта и отдавать файл синхронно.

### 2.6. Канонический Gateway-путь для классификаторов

**Контекст:**
- В Gateway routing table есть `/classifiers/*`.
- В registry docs есть `/registry/classifiers/tree`.
- UI сейчас сначала пробует `/classifiers/tree`, затем fallback `/registry/classifiers/tree`.

**Вопрос:**
> Какой путь канонический? Нужно зафиксировать один маршрут в Gateway и убрать fallback в UI.

### 2.7. Синхронизация mock-данных Registry и Classifiers

**Контекст:**
- Классификатор MKS сейчас: `47 / Судостроение`.
- Registry-документ имеет `mks_oks_code: 31.240`.
- Из-за этого в разделе «Судостроение» документов 0. UI ведёт себя корректно, но тестовые данные не позволяют проверить полный UX.

**Вопрос:**
> Можно ли обновить seed/mock-данные так, чтобы хотя бы один документ имел `mks_oks_code` ветки `47` (Судостроение)? Или это осознанное разделение (МКС — другая классификация)?

**Решение:**
- Добавить второй seed-документ с `mks_oks_code: 47.020`.
- Классификатор (МКС) — системная часть, извлекается из документа и не меняется произвольно. Код `31.240` у первого документа корректен и остаётся.

### 2.8. Нужен ли серверный endpoint загрузки документа по URL?

**Контекст:**
- Сейчас внешний поток Gateway описывает `POST /drafts` для файла (multipart/form-data).
- Для надёжной загрузки по ссылке лучше иметь backend endpoint, который сам скачивает URL, валидирует файл и создаёт draft.

**Вопрос:**
> Будет ли реализован `POST /drafts/upload-url` (или аналог) в Gateway/Orchestrator?

**Рекомендация:**
- Если не в MVP, зафиксировать это в roadmap и оставить client-side fallback в UI с пометкой `// TODO: replace with server-side upload when backend ready`.

---

### 2.9. Какие endpoints считаются публичными для pipeline artifacts/logs?

**Контекст:**
- В Gateway routing table `/api/v1/tasks/*` помечен как internal.
- UI использует его для админ-мониторинга — фактически endpoint работает и возвращает данные, передаваемые между сервисами.

**Решение:**
- `/tasks/*` уже работает и возвращает актуальные данные. UI продолжает использовать.
- **Предложение:** зафиксировать публичный контракт:
  - `GET /tasks/{task_id}` — статус и метаданные пайплайна (доступно admin)
  - `GET /tasks/{task_id}/steps` — поэтапный лог шагов
  - `GET /drafts/{draft_id}/tasks` — список задач для черновика

### 2.10. Какой финальный Auth/Admin namespace?

**Контекст:**
- Сейчас UI использует `/admin/users`, `/admin/roles`, `/admin/audit`.
- В части документации встречаются также `/users/*`, `/roles`, `/audit`.

**Вопрос:**
> Какой namespace канонический для административных операций? Все под `/admin/*` или распределённые?

**Рекомендация:**
- Зафиксировать `/admin/*` как единый namespace. Убрать упоминания `/users/*`, `/roles`, `/audit` из документации или объявить их устаревшими.

## 3. Ветки-кандидаты на удаление

### 3.1. Можно удалить после подтверждения

Эти ветки — наши, уже являются предками `origin/develop` и текущей рабочей UI-ветки:

| Ветка | Где | Почему можно удалить |
|-------|-----|----------------------|
| `codex-ui-final-docs-readme` | local + origin | Документационные правки уже вошли в develop и текущую UI-ветку. |
| `codex/ui-final-docs-readme` | local + origin | Дубликат предыдущей docs/readme-ветки, тоже уже вошёл в develop. |

**Команды:**
```bash
git branch -d codex-ui-final-docs-readme
git branch -d codex/ui-final-docs-readme
git push origin --delete codex-ui-final-docs-readme
git push origin --delete codex/ui-final-docs-readme
```

### 3.2. Не удалять без отдельной проверки

Эти ветки старые или промежуточные, но **не являются предками** `origin/develop`:

| Ветка | Где | Причина осторожности |
|-------|-----|----------------------|
| `feature/ui-final-gateway-current` | local + origin | Старая основная UI/Gateway-ветка, но не слита в develop полностью по git-графу. |
| `feature/ui-final-gateway-spike` | local only | Старый эксперимент Gateway wiring; не предок develop. |
| `feature/ui-import-frontend-v1` | local + origin | Содержит memo/материалы frontend-v1; не предок develop. |
| `ui-v1-meeting-2026-06-09` | local, upstream `origin/feature/ui-import-frontend-v1` | Локальная ветка с memo встречи 09.06; не предок develop. |

**Рекомендация:**
- Перед удалением каждой ветки выполнить `git log --oneline <ветка> ^develop` и проверить, есть ли коммиты, не вошедшие в develop.
- Для `feature/ui-final-gateway-current` особенно важно: если там есть код, не перенесённый в текущую рабочую ветку, — сделать cherry-pick или ручной перенос.
