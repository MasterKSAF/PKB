## Итоги встречи

### Принятые решения и договорённости
1. **Переход к этапу предфинального тестирования бэкенда**  
   - При успешном прохождении тестов сегодня вечером завтра будет развёрнут веб-интерфейс.  
   - Презентация системы запланирована на **8 число**. Оставшиеся две недели делятся на:  
     - ~1 неделя – отладка качества (работа с эталонами),  
     - оставшееся время – загрузка документов и подготовка демонстрации.

2. **Реорганизация задач по трём ключевым направлениям**  
   - **Направление 1** – отладка инфраструктуры и мониторинга (часть людей).  
   - **Направление 2** – загрузка реальных документов через веб и проверка полного цикла (подключается «пятая группа» тестирования).  
   - **Направление 3** – подготовка эталонов для парсера, конвертера и RAG‑поиска. Работа начинается немедленно, не требует полностью готовой системы.  
   - Деление на старые группы формально сохраняется, но меняется содержание деятельности.

3. **Подход к эталонам качества**  
   - Принят метод «обратного хода»:  
     - PDF → идеальная распарсенная страница → разбивка на идеальные секции → разбивка на идеальные сегменты парсинга (Open Data Loader).  
     - Полученные секции/JSON фиксируются как эталон.  
     - Затем на вход сервиса подаётся PDF, и его выдача доводится до эталонного результата с помощью нейросети.  
   - Без эталонов нейросеть «врёт» и не способна стабильно улучшаться.

4. **Выборка документов для тестирования**  
   - Отвечает **Семён**.  
   - Первичный объём – **10 русскоязычных документов из области Морского регистра** (максимально разнообразных по размеру, структуре, наличию таблиц/картинок).  
   - Англоязычные документы на данном этапе исключены, чтобы не раздувать требования.  
   - Если первая десятка будет обработана успешно и останется время – можно добавить ещё документы.  
   - Документы для тестов обязательно поместить в Git (с оговорками по размеру) и/или на сервер.

5. **Хранение тестовых данных**  
   - Все файлы, участвующие в тестировании (JSON эталонов, PDF), должны храниться в репозитории.  
   - Крупные файлы (>1 МБ) класть в Git тяжело – для них возможно использование серверного хранилища. Пока Семён собирает документы на Google Диске и даст ссылки.

6. **Мониторинг и логирование**  
   - Все сервисы должны быть подключены к системе мониторинга.  
   - За инструкцию и шаблоны отвечает **Диана**, в репозитории создана папка `monitoring-service`.  
   - Итоговый чекер Игоря будет дополнен тестом на подключение мониторинга (позже, не сейчас).  
   - Перевод интерфейса мониторинга на русский невозможен, пользоваться через Яндекс.Браузер.

7. **Ограничения на количество запросов**  
   - В сервисах парсинга PDF достаточно защитного лимита на размер внутреннего списка обрабатываемых документов (например, 15). Параметр выносится в конфиг.  
   - Для сервисов RAG (Павел) аналогично – ограничение на длину очереди (10–20 пакетов). Оркестратор также будет контролировать поток.

8. **Развёртывание второй копии RAG-сервисов**  
   - Текущая архитектура не рассчитана на два одновременно активных RAG‑индекса, поэтому полноценное сравнение возможно только через развёртывание **второй копии всей системы**.  
   - Павел подтвердил готовность своих сервисов (rakebuilder и rakesetcher). Он передаст их Игорю Колесову для развёртывания второй копии.

### Технические детали

#### Архитектура и пайплайны
- **Сервисы**: парсер (с Open Data Loader), конвертер, RAG‑билдер (rakebuilder), RAG‑сетчер (rakesetcher), оркестратор, мониторинг‑сервис, веб‑интерфейс.  
- **Целевой пайплайн обработки документов**: PDF → парсер (извлечение структуры) → конвертер (стандартизация) → индексация в RAG.  
- **Тестовый пайплайн для эталонов** (обратный):  
  1. Из PDF вручную/нейросетью получается идеальная страница.  
  2. Страница делится на секции (эталонные секции).  
  3. Секции преобразуются в эталонные JSON‑куски, соответствующие выходу парсера.  
  4. Сервис получает на вход PDF и должен выдать структуры, максимально близкие к эталонным.

#### Форматы данных и API
- Выход парсера: JSON с метаданными и блоками документа, структура описана в документации API (таблица «красненьким»).  
- Эталонный JSON – не только структура, но и **содержимое** секций.  
- Взаимодействие между сервисами: REST/внутренние вызовы, контроль через оркестратор.

#### Инструменты и технологии
- **Open Data Loader** – извлечение контента из PDF, множество опций.  
- **Очереди задач**: Celery признан избыточным для быстрого парсинга PDF; для ограничений используются простые списки в памяти с лимитами.  
- **Синхронизация и ограничения**: семафоры/мьютексы (Диана), фиксированный лимит очереди (Павел).  
- **Эмбеддинги**:  
  - Продуктивно будет использоваться облачный **Qwen**, ключи будут прописаны на сервере.  
  - Локально у Павла сейчас стоит заглушка‑провайдер (генерит нули).  
- **Мониторинг**: отдельный сервис, настройка через копирование файлов и конфигов (инструкция в `monitoring-service`). Требует структурированного логирования с едиными полями.  
- **Тестирование**: чекер Игоря с пакетным запуском тестов, два батника – для основного и альтернативного сервисов.  
- **Хранение**: Git для кода и эталонов, сервер для больших файлов, Google Диск как временный сборщик.

#### База данных
- Упомянуты «таблицы базы данных» в контексте сервисов RAG‑билдера и сетчера, без раскрытия структуры.

#### Метрики
- Основная метрика качества на текущем этапе – совпадение выхода сервиса с эталонным содержимым (точное соответствие секций).

### Особенности и проблемы

#### Узкие места и ограничения
1. **Катастрофическая нехватка времени**: 2 недели до презентации, из которых реальная отладка качества – около недели.  
2. **Зависимость от эталонов**: без них нейросеть работает нестабильно и не даёт нужного качества. Подготовка эталонов – творческая и трудоёмкая задача.  
3. **Инфраструктура эмбеддингов**: не финализирована, ключи для Qwen ещё не распределены, локально используется заглушка, что мешает полноценному тестированию RAG.  
4. **Крупные файлы**: Git плохо работает с PDF большого размера, альтернативное хранилище пока не определено.  
5. **Низкая активность участников**: Игорь отметил, что не может ставить задачи каждому лично, так как это неэффективно; ожидается самостоятельная работа в «песочницах».  
6. **Несовместимость двух RAG‑индексов**: система не поддерживает одновременную работу двух конкурирующих вариантов, требуется поднимать второй экземпляр целиком.  
7. **Мониторинг**: внедрён, но ещё ни разу не тестировался на реальном приёме данных от сервисов. Нет автоматической проверки в чекере.  
8. **Языковой барьер**: интерфейс мониторинга на английском, простого способа русификации нет.

#### Баги и нестыковки
- Участники периодически теряются в растущей документации; нейросеть «теряется» в больших инструкциях.  
- В парсере после первых изменений у всех были ошибки (уже исправлены, сервис Дианы работает стабильно).  
- У Павла были проблемы с запуском предоставленного теста (прокси, путаница), но в итоге тесты прошли успешно, за исключением одной массовой ошибки (характер не уточнён).

### Контекст и договорённости по процессам

#### Ответственные
- **Игорь (главный)**: общая координация, чекер, критерии приёмки, помощь в архитектурных вопросах.  
- **Диана**: сервис парсинга, приведение к эталонной структуре, документация по мониторингу и логированию.  
- **Павел**: сервисы RAK‑билдера и сетчера, взаимодействие с Колесовым по развёртыванию.  
- **Семён**: отбор и предоставление тестового корпуса документов.  
- **Евгений**: в контексте первой группы, задачи ставятся в рамках общего направления (детали не определены, ожидается самостоятельное подключение).  
- **Пятая группа**: реальное эксплуатационное тестирование через веб.

#### Сроки
- **Сегодня‑завтра**: первый веб, старт сбора документов Семёном.  
- **Завтрашнее совещание**: отчёт о документах, статус веба.  
- **Через неделю**: завершение первичной отладки качества, работающая цепочка эталонов.  
- **8 число**: презентация.

#### Коммуникация и условия продолжения
- Основной канал – записи совещаний, чат первой группы (будут выложены сразу после встречи).  
- Техническая документация – Git (backend/docs, monitoring-service).  
- Критические изменения и новые требования Игорь будет присылать лично (например, по почте).  
- Документы для тестов сначала собираются на Google Диске, затем переносятся в Git и/или на сервер.  
- Условие успешной презентации – стабильно работающий пайплайн на 10 разнородных русскоязычных документах из предметной области Морского регистра.
