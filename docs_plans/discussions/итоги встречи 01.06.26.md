## Итоги встречи, основные решения, планы и договорённости

**Дата встречи:** (по контексту – текущая неделя)  
**Участники:** разработчики сервисов (Роман, Виталий, Павел, Диана и др.)

---

### 1. Технические решения и выводы

#### 1.1. Идентификаторы (ID)

- **Принято:** использовать **int (bigint)** вместо UUID.

- **Обоснование:**
  
  - Int-ID строго возрастают, что нужно для функционала чата («дать сообщения новее чем…»).
  
  - Индексы с int работают эффективнее (ложатся в хвост).
  
  - UUID не даёт реальных преимуществ для текущих задач, только усложняет базу.

- **Исключение:** у документа пока остался UUID, но принято решение пересмотреть – генерировать ID документа только при записи в БД, тогда можно использовать int.

#### 1.2. Модели эмбедингов

- **Локальное тестирование:** использовать **Qwen 4B** (или 8B, если хватает памяти).

- **Lama не подходит** – она не заточена под эмбединги (медленная, нет API для re-ranking).

- Для продуктивного сервера – отдельный сервер эмбедингов (например, Infinity), который требует Linux и настройки. На Windows тестировать сложно, поэтому пока в сервисах делать двойной режим: либо локальная загрузка модели в Python, либо обращение к внешнему серверу эмбедингов.

#### 1.3. Версионность документов (ключевое разграничение)

- **Версии загрузки** – разные попытки загрузить один документ (скан, PDF, DOCX). Они хранятся в пайплайне обработки, привязаны к Task ID, в реестр документов не попадают. Это уже реализовано.

- **Редакции документов** – юридические изменения, которые отменяют или заменяют предыдущую редакцию. Эта тема **не проработана**, требует отдельного обсуждения с заказчиком (Семёном).

- **Решение:** на текущей неделе провести встречу с Семёном по редакциям – как учитывать даты вступления в силу, отмену, выбор актуальной редакции на заданную дату.

#### 1.4. Формат документ-контейнера (результат парсинга)

- В JSON добавлены новые типы блоков: **листы, параграфы, футеры, объект шрифта** (жирный, курсив, подчёркнутый) – для форматирования при отображении.

- **Для индексации (RAG/поиск):** передаётся агрегированная версия – текст, таблицы в Markdown. Детальная структура (ячейки, объекты) нужна только для отображения, не для поиска.

- **Таблицы:** передаются и как объектная структура, и как Markdown. Индексация будет по Markdown. Вопросы по индексации таблиц вынесены на обсуждение второй группы (RAG-поиск).

#### 1.5. Парсинг и файловое хранилище

- Сервис парсинга получает **ссылку на файл** (из MinIO или локального хранилища), скачивает, обрабатывает, возвращает JSON. Сам ничего не сохраняет.

- **Картинки** внутри документа: парсер сохраняет их в хранилище (MinIO) и в JSON вставляет ссылки. Нужен доступ на запись.

- Будем использовать компонент-обёртку (Андрис), который может писать на диск вместо MinIO.

#### 1.6. Query сервис (ковер-сервис)

- **Новое API для точечных обновлений чата** – 4 метода вместо одного прежнего (читать только изменения, дождаться ответа на сообщение, читать последние N сообщений и т.д.).

- Нужно реализовать взаимодействие с Rag Search через заглушки (с флагами включения/выключения) и адресацию.

### 2. Планы и договорённости по срокам

#### 2.1. Готовность сервисов

- **Срок:** сервисы нужны в ветке `develop` **к понедельнику** (следующей недели) после постановки задачи.

- Вторник–среда – отладка, попытка развернуть на сервере.

- Если сдавать только к среде, на отладку не останется времени – следующий спринт будет сорван.

#### 2.2. Деплой и CI/CD

- **Ответственный за настройку деплоя:** Игорь.

- Механизм: **GitHub Actions** (CI/CD pipelines). Варианты:
  
  - Кнопка manual workflow (менее удобно при 10 сервисах).
  
  - **Автоматический деплой по коммиту в специальную ветку** (например, `release-<service>`). Принят как основной – более управляемый.

- Каждый сервис получает свой `pipeline.yaml` (образец даст Игорь). Разработчику не нужно самостоятельно упаковывать Docker-образы, достаточно закоммитить исходники.

- Базы данных изолированы по схемам; доступ к чужим БД только через API.

#### 2.3. Миграции базы данных

- Пока **одноразовые** – при изменении схемы БД пересоздаём базу (совместимость не требуется).

- После фиксации первой рабочей версии и начала наполнения документами – переходим к патчевым миграциям (накат изменений).

- Скрипты для создания структуры БД и загрузки справочников (классификаторов) будут общими.

#### 2.4. Ближайшие встречи

- **На этой неделе:**
  
  - Обсуждение **редакций документов** с Семеном (юридическая версионность, даты действия, отмена).
  
  - Возможно, встреча второй группы (RAG-поиск) по деталям индексации таблиц и re-ranking.

---

### 3. Договорённости по процессу

- Разработчики коммитят код в `develop` (или свою feature-ветку) в папку `backend/<service>`.

- Код должен содержать конфигурацию (например, `.env` или локальный конфиг) для переключения между заглушками и реальными сервисами, режимами эмбедингов (локально/сервер).

- **Мониторинг** – после деплоя разработчик проверяет работу своего сервиса через панель мониторинга (логи, метрики), а не заходит на сервер заказчика.

- За координацию деплоя и инфраструктуры отвечает Игорь; остальные помогают с настройкой пайплайнов под свои сервисы (написание `pipeline.yaml` по образцу).

---

### 4. Открытые вопросы (требуют решения)

- Редакции документов – механизм учёта во времени, фильтрация по дате, связь с чанками.

- Выбор конкретного эмбединг-сервера для продуктовой среды (Infinity и др.), способ его развёртывания на Windows (через Docker с персистентным хранилищем).

- Детали индексации таблиц в RAG – как обеспечить поиск по содержимому ячеек без потери структуры.
