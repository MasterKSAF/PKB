## Короткий вывод

Из другой админки стоит забрать не внешний вид один в один, а рабочую модель: плотный admin-layout, список/дерево слева, карточка редактирования справа, LLM-извлечение метаданных, ручная проверка, классификация, сохранение в реестр и работа с версиями документов.

Верхнюю навигацию UI Final лучше не перегружать новой большой вкладкой. Основные функции нужно встроить в существующие разделы:

| Вкладка UI Final | Целевая роль |
| --- | --- |
| `База знаний` | Пользовательская витрина: разделы, поиск, список документов, preview, скачать. Без редактирования. |
| `Обработка базы знаний` | Рабочее место администратора знаний: загрузка, черновики, LLM-метаданные, ручная проверка, классификация, approve/reject, реестр документов, версии, очередь и журнал. |
| `Администрирование` | Пользователи, роли, права, Registry-редакторы классификаторов, терминологии и неизвестных кодов. |
| `QA` | Метрики качества, ошибки обработки, отчеты по качеству. Не смешивать с ручным редактированием документов. |

## Что полезного забрать

1. Плотный layout для админских сценариев: слева список/таблица/дерево, справа карточка выбранной сущности.
2. Сценарий загрузки документа: файл -> LLM-анализ первых страниц -> JSON метаданных -> ручная правка -> сохранение.
3. Сравнение метаданных: `извлечено автоматически` против `подтверждено вручную`.
4. Raw JSON результата LLM в свернутом техническом блоке.
5. Autocomplete по классификаторам: MKS, OKSTU/OKS, UDC, внешние классификаторы, PKB/categories.
6. Реестр документов как admin-экран: таблица документов и карточка выбранного документа.
7. Управление версиями документа: список версий, открыть, скачать, удалить, сравнить.
8. Единый полноэкранный preview документа с поиском по тексту, страницами и скачиванием.
9. История действий с документом: загрузка, изменение метаданных, принятие, отклонение, новая версия.
10. Явное разделение пользовательского просмотра и административного редактирования.

## Целевая структура вкладок

### База знаний

Оставить только пользовательские функции:

- строка поиска по базе знаний;
- фильтр области поиска: вся база или выбранный раздел;
- карточки/разделы базы знаний;
- провал внутрь раздела;
- компактный список документов раздела;
- preview выбранного документа справа;
- полноэкранный preview;
- поиск внутри preview;
- скачивание документа.

Не добавлять сюда:

- редактирование метаданных;
- approve/reject;
- управление версиями;
- редактирование классификаторов;
- технические очереди и журналы.

### Обработка базы знаний

Сделать основной рабочей зоной администратора документов.

Внутренние режимы:

1. `Черновики`
2. `Реестр документов`
3. `Очередь и журнал`

#### Черновики

Назначение: загрузить файл, получить LLM/preview-разбор, проверить метаданные, принять или отклонить.

Экран:

- слева компактный список черновиков;
- сверху над списком: загрузка файла, сортировка, фильтр статуса;
- справа карточка выбранного черновика;
- в карточке: preview, метаданные, классификация, сравнение с LLM, raw JSON, действия.

Действия:

- загрузить PDF/DOCX;
- создать draft;
- запустить preview/LLM-разбор;
- открыть preview;
- вручную исправить метаданные;
- назначить классификацию;
- принять в базу;
- отклонить с комментарием;
- удалить черновик.

#### Реестр документов

Назначение: администрирование уже принятых документов.

Экран:

- слева таблица документов;
- справа карточка выбранного документа;
- над таблицей: поиск, фильтры, сортировка.

Поля таблицы:

- код документа;
- название;
- тип источника;
- год/эра;
- юрисдикция;
- классификация;
- дата загрузки;
- текущая версия.

Карточка документа:

- основные метаданные;
- связи с классификаторами;
- секции/разделы документа;
- статус обработки/индексации;
- история ошибок;
- действия с документом.

Действия:

- открыть preview;
- скачать файл;
- посмотреть версии;
- загрузить новую версию, если backend поддерживает;
- удалить документ, если backend поддерживает;
- открыть историю обработки.

#### Очередь и журнал

Назначение: технический контроль обработки.

Оставить:

- очередь обработки;
- журнал обработки;
- ошибки обработки;
- ссылка на документ или черновик;
- фильтры по статусу, дате и типу операции.

Не смешивать этот режим с карточкой редактирования метаданных.

### Администрирование

Оставить и развить Registry-редакторы.

Внутренние разделы:

- пользователи и роли;
- права доступа;
- административный журнал;
- классификаторы;
- терминология;
- неизвестные коды.

Классификаторы:

- список;
- дерево;
- добавить корневой узел;
- добавить дочерний узел;
- редактировать узел;
- удалить узел;
- import CSV/XLSX, если backend стабильно поддерживает.

Терминология:

- таблица терминов;
- карточка термина;
- raw term;
- standard term;
- normalized value;
- type;
- synonyms;
- blocked;
- definition;
- import CSV/XLSX, если backend стабильно поддерживает.

Неизвестные коды:

- список неизвестных кодов;
- привязка к классификатору;
- создание нового узла из неизвестного кода;
- accept/reject с комментарием администратора.

## Новые UI-блоки

### 1. Карточка проверки черновика

Состав:

- заголовок документа;
- файл и дата загрузки;
- текущий статус draft;
- кнопки preview, запустить разбор, принять, отклонить, удалить;
- блок метаданных;
- блок классификации;
- блок сравнения с LLM;
- raw JSON.

### 2. Сравнение метаданных

Таблица:

| Поле | Извлечено автоматически | Подтверждено вручную | Статус |
| --- | --- | --- | --- |
| Код документа | значение LLM | редактируемое значение | совпало/изменено/пусто |
| Название | значение LLM | редактируемое значение | совпало/изменено/пусто |
| Тип источника | значение LLM | редактируемое значение | совпало/изменено/пусто |
| Год/эра | значение LLM | редактируемое значение | совпало/изменено/пусто |
| Юрисдикция | значение LLM | редактируемое значение | совпало/изменено/пусто |
| Издатель | значение LLM | редактируемое значение | совпало/изменено/пусто |

### 3. Raw JSON

Свернутый блок для администратора:

- исходный JSON LLM;
- нормализованный JSON Gateway;
- ошибки парсинга, если есть;
- confidence, если backend отдает.

### 4. Классификация документа

Поля:

- MKS;
- OKSTU/OKS;
- UDC;
- External;
- PKB/categories.

Поведение:

- autocomplete по коду и названию;
- очистка значения;
- множественный выбор для categories, если backend подтверждает M:N;
- подсказка, если выбран неизвестный код.

### 5. Preview документа

Единый компонент для всех сценариев:

- база знаний;
- обработка базы знаний;
- реестр документов;
- чат.

Функции:

- открыть на весь экран;
- страницы вперед/назад;
- поиск по тексту;
- подсветка найденного;
- скачать;
- показать источник/метаданные.

### 6. Версии документа

Окно или боковая панель:

- имя файла;
- дата загрузки;
- размер;
- автор/источник;
- статус версии;
- открыть;
- скачать;
- удалить;
- сравнить.

### 7. Сравнение версий

Экран:

- версия A слева;
- версия B справа;
- различия по метаданным;
- ссылки на preview обеих версий;
- различия по статусу обработки/индексации.

## Пошаговая реализация

### Этап 1. Контракты и типы

1. Сверить текущие Gateway endpoints по drafts, documents, registry, classifiers, terminology, versions.
2. Зафиксировать frontend-типы:
   - `DraftItem`;
   - `DraftMetadata`;
   - `ExtractedMetadata`;
   - `DocumentRegistryItem`;
   - `DocumentVersion`;
   - `ClassifierRef`;
   - `DocumentClassification`;
   - `DocumentProcessingEvent`.
3. Убрать неявные поля, которые не подтверждены Gateway.
4. Все неподтвержденные поля оставить за feature flag или не показывать.

### Этап 2. Черновики

1. Перестроить `Обработку базы знаний` на рабочую модель: список черновиков слева, карточка справа.
2. Добавить явный блок `Метаданные`.
3. Добавить блок `Сравнение с автоматическим разбором`.
4. Добавить свернутый `Raw JSON`.
5. Подключить сохранение ручных правок в тот endpoint, который подтвердит backend.
6. Перед approve отправлять финальные подтвержденные метаданные.
7. Reject делать с обязательным комментарием, если это подтвердит backend.

### Этап 3. Классификация

1. Подключить autocomplete к Registry classifiers.
2. Добавить выбор MKS/OKSTU/UDC/External.
3. Добавить выбор PKB/categories.
4. Для categories поддержать множественный выбор, если backend подтверждает M:N.
5. При неизвестном коде давать переход в `Администрирование -> Неизвестные коды`.

### Этап 4. Реестр документов

1. Добавить внутренний режим `Реестр документов` в `Обработку базы знаний`.
2. Сделать таблицу принятых документов.
3. Сделать карточку выбранного документа.
4. Подключить document detail, status, sections, errors, history.
5. Добавить preview и скачать.
6. Добавить редактирование/удаление только если backend подтвердит endpoints.

### Этап 5. Версии

1. Добавить окно `Версии документа`.
2. Подключить список версий.
3. Добавить preview/download конкретной версии.
4. Добавить загрузку новой версии, если backend поддерживает.
5. Добавить удаление версии, если backend поддерживает.
6. Добавить сравнение версий по метаданным.

### Этап 6. Registry-редакторы

1. Доработать дерево классификаторов под сценарий из админки.
2. Сделать создание корневого узла и дочернего узла максимально очевидным.
3. В unknown codes добавить форму принятия кода как нового узла классификатора.
4. В terminology проверить поля синонимов, scope, blocked, definition.
5. Import CSV/XLSX включать только после стабильного backend-контракта.

### Этап 7. Permissions и audit

1. Проверить права на каждую функцию:
   - просмотр базы знаний;
   - загрузка документа;
   - approve/reject;
   - редактирование метаданных;
   - удаление документа;
   - управление версиями;
   - управление классификаторами;
   - управление терминологией.
2. Показывать disabled-состояние или скрывать действие по permissions.
3. Отображать audit/history по документу.
4. В UI не имитировать успешное действие, если Gateway вернул ошибку.

### Этап 8. Проверка

1. `npm run lint`.
2. `npm run build`.
3. Smoke с Gateway:
   - вход;
   - загрузка файла;
   - draft list;
   - preview/LLM;
   - ручная правка метаданных;
   - классификация;
   - approve;
   - появление документа в реестре;
   - preview документа;
   - версии;
   - Registry editors.
4. Отдельно проверить demo-режим, чтобы он не подменял Gateway-ошибки в продуктивном режиме.
