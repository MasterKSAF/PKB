Ниже собраны детальные итоги встречи, сгруппированные по темам: основные решения, планы, договорённости и технические особенности.

### 1. Статус чекера и пайплайнов

**Результаты:**

- Локальный запуск чекера с полным пайплайном (от загрузки документа до поиска) выполнен успешно, ошибок нет.
- Чекер использует примитивный быстрый эмбеддер (300 измерений) и прогоняет все сервисы на процессоре.
- Реализовано 8 типов пайплайнов: работа с документами, чат, реестр, жизненный цикл документа, админка, черновики, оркестратор, полный цикл.

**Проблемы:**

- В RackBuilder не сработала проверка базы (пометка «крестик»), требуется исправить код.
- Частично остаются расхождения типов `string` и `integer` в API. В RackBuilder исправлено полностью, в парсере Диана исправила в новой версии, но тестируется пока старая.
- Зафиксированы предупреждения по сервисам: конвертер, парсер, query-сервис, registry (см. раздел «Стыковка API»).

### 2. База данных и файловое хранилище

**Решения и договорённости:**

- **База данных:** общая, разделена по схемам. Каждый сервис создаёт и обслуживает свою схему самостоятельно. Исключение – RecSearch, работающий с готовой базой.
- **Файловое хранилище (MinIO, S3-совместимое):**
  - Имена бакетов фиксируются: `files` для документов и `images` для картинок. Менять не планируется, документация будет приведена в соответствие.
  - Ключ документа – SHA-256 хэш содержимого (без расширения). Это гарантирует уникальность и обнаружение дубликатов на уровне хранилища.
  - Ключ картинки – формат с ID задачи или черновика, подчеркиванием, номером и расширением (готовы обсуждать оптимальный вариант). Диана зафиксирует в документации.
  - Диана уберёт из своей логики требование расширения `.pdf` в `FileKey` (ключ не обязан нести расширение).
- **Развёртывание:** MinIO запускается отдельным Docker-контейнером, аналогично Postgres и Redis. Настройки бакетов и прав пока делаются администратором с полными правами, в будущем уточнят.

### 3. Архитектура и развёртывание

**Особенности и договорённости:**

- В чекере все 10 сервисов для экономии памяти упакованы в один Docker-образ (~1 ГБ). На сервере каждый сервис будет в отдельном контейнере.
- Оркестратор (Kubernetes) не используется. Масштаб – до 50 пользователей, каждый сервис в одном экземпляре, без распределённости.
- Будет собственный gateway; для управления достаточно команд старта/остановки контейнеров.
- На этой неделе ожидается развёртывание системы на сервере, что позволит подключить веб-клиент к реально работающей системе.

### 4. Качество и тестирование

**Планы:**

- Фокус смещается на качество. Определены два направления тестов:
  1. Тесты на сложную логику (нестандартные аномалии, сложные цепочки обработки).
  2. Тесты на корректность и высокое качество парсинга конкретных данных.
- Сервис Query играет ключевую роль в качественной обработке чанков и обогащении запросов, его качеству – особое внимание.
- Индексация требует тесной связки RackSearch и Query.
- По сервису OCR решение пока не принято. Если он не появится, основная нагрузка по первичной обработке документов ляжет на сервис парсинга Дианы.

### 5. Стыковка API и документации

**Текущие проблемы (из отчёта чекера):**

- **Конвертер:** пути API не полностью соответствуют документации; некоторые ID приходят как строка вместо `integer`, местами `GUID` вместо `int`.
- **Парсер:** проблема с требованием расширения в `FileKey` (будет исправлена).
- **Query-сервис:** одно предупреждение (суть не раскрыта, но зафиксировано).
- **Registry:** требует завершающие слэши в URL (мелочь, нужно поправить).
- **RackBuilder:** возможно, остался код, связанный с авторизацией (`GUID`), хотя авторизация уже убрана. Игорь проверит.

**Организационные решения:**

- Разработчикам рекомендовано оперативнее и внимательнее реагировать на нестыковки с документацией, так как прошедшая неделя ушла именно на стыковку, а не на логические ошибки.

### 6. Система мониторинга (SigNoz)

**Предложенное решение:**

- Инструмент: **SigNoz** (в речи – Signos). Использует **OpenTelemetry** для сбора логов, трейсов и метрик в одном сборщике.
- Хранение данных: **ClickHouse**.

**Внедрение в сервисы (минимально необходимый объём):**

1. Добавить библиотеки в `requirements.txt`.
2. Скопировать в проект самописную библиотеку телеметрии (лежит в репозитории `monitoring-service`).
3. В `main` прописать импорт и инициализацию логгера и трейсов (точный код даст Диана).
4. Метрики и ручные трейсы – опционально; базовые метрики (CPU, память) подключаются автоматически.
5. Логирование должно быть настроено в каждом сервисе (уровни: info, debug, warning, error, exception). Форматы полей жёстко фиксированы в библиотеке.

**Интеграция на уровне проекта:**

- Система мониторинга создаёт свою Docker-сеть (`signoz-network`). Общий `docker-compose.yml` должен билдить образы сервисов и подключать их к этой сети.
- Примеры `docker-compose`, тестовые сервисы A/B/C и инструкции размещены в ветке `monitoring-service`.

**Нерешённые вопросы:**

- Необходимо проработать сквозную трассировку между микросервисами: `trace ID` должен задаваться инициатором (вебом) и передаваться по цепочке. Текущая реализация проверена только внутри одного сервиса.

**Договорённости:**

- Диана снимет видеоинструкцию по установке системы мониторинга и настройке сервисов.
- Внедрение мониторинга должно быть выполнено в течение оставшихся двух недель. На этой неделе ожидается добавление необходимых правок в сервисы.
- Для тестирования разработчикам рекомендовано локально развернуть систему мониторинга, используя предоставленные примеры.
