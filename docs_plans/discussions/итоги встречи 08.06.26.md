### Основные решения

- **Файловое хранилище и именование файлов**
  
  - В качестве имени файла в S3-хранилище используется **хэш содержимого (SHA-256)**. Это гарантирует уникальность и позволяет автоматически выявлять дубликаты. Для картинок можно использовать идентификаторы, главное что бы имена были уникальные.
  - Глобально утверждены **два бакета**: `files` (документы) и `images` (картинки). Дробления на множество бакетов не будет.
  - Папки внутри бакетов (например, по ID задачи/черновика) пока можно оставить для визуального удобства, но главное это унифицировать. Если они станут не нужны, от них можно отказаться.
  - Связь файлов и сущностей будет храниться в **PostgreSQL** (в таблицах документов и их секций). Общий компонент для работы с хранилищем унифицируют, чтобы никто не придумывал свои правила.

- **Парсинг и превью**
  
  - Вместо отдельных endpoint’ов `/preview` и `/parse` вводится **один общий метод `parse`** с опциональным флагом `mode=preview`.
  - Если парсер поддерживает превью — отдает его; если нет — возвращает полный документ и в метаданных указывает `mode=full`. Pipeline запоминает это и не будет повторно вызывать полный парсинг.
  - Новая версия API лежит в ветке `docs` и будет выложена в `develop`.

- **Классификаторы и UI**
  
  - Неизвестные классификаторы, найденные в документах, будут попадать в таблицу **`pending classifier`** и ждать решения администратора. Документ при этом не пропадает.
  - В веб-интерфейсе во вкладке «Метаданные» нужно показывать детали документа, а также статус загрузки и проблемы с классификаторами. Это делается для отладки и удобства.
  - Поскольку заказчик не даёт обратной связи по UI, команда приняла решение **дозаполнять вкладку «Метаданные»** и фильтры неклассифицированных документов по своему усмотрению, фиксируя то, что уже сделано.

- **Мониторинг и логирование**
  
  - Логи должны быть **структурированными** (совместимыми с OpenTelemetry). Уровни логирования – стандартные (`debug`, `info`, `error`, `warning`).
  - Срок хранения логов ограничен **одной неделей**, в выбранной системе это будет настроено по умолчанию.
  - Систему мониторинга (не Grafana, со встроенными трейсами и метриками) решено собрать с минимальными правками как идеальный вариант для текущей ситуации.

### Особенности процесса

- **Service Checker:** Инструмент поднимает всю инфраструктуру локально в одном общем контейнере для быстрой проверки работоспособности всех сервисов. Первый запуск рекомендуется делать через AI-ассистента. Утилита станет обязательной для верификации.
- **Отсутствие заказчика:** Обратная связь от заказчика по интерфейсам отсутствует, поэтому команда действует экспериментально, дополняя функционал по своему усмотрению с опорой на имеющиеся API.
- **Сервис эмбеддингов:** Отказались от встраивания моделей в микросервисы. Вместо этого появится выделенный сервис **Infinity** (OpenAI-совместимое API), который будет обслуживать запросы от `RagBuilder` и `RagSearch`, оптимально утилизируя GPU. По этой причине сервисы сейчас работают с ошибками в ServiceChecker.
