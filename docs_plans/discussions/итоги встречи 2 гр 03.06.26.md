По итогам предоставленной видеостенограммы совещания можно выделить следующие ключевые итоги, решения и договоренности.

## 1. Основные результаты и прогресс

- **Первичное тестирование успешно пройдено**: все сервисы (на примере RagBuilder) запустились и выдали первичные вызовы. Коллеги поздравили друг друга с этим событием.
- **Запрототипированы все сервисы**, кроме конвертера-валидатора (его реализация еще ожидается). Остальные сервисы представили первичные версии с API.

## 2. Текущее состояние и ближайшие планы по сервисам RAG

Выделены три основных сервиса:

- **RagBuilder** – построение индекса.
- **RagSearch** – извлечение релевантных чанков (гибридный поиск: векторный + полнотекстовый BM25).
- **ServiceQuery** (обработчик с LLM и цитированием).

**Планы развития:**

- Реализовать гибридный поиск (это ближайшая задача).
- Добавить механизм цитирования источников (как в Perplexity – серые ссылки на документы).
- Реализовать графовую часть: заглядывать на один шаг во внешние хосты, на которые есть ссылки, а также механизм периодической привязки ссылок к ID документов (по мере их загрузки).
- В дальнейшем – оценка адекватности (RRP-алгоритм) и передача в главную LLM.

## 3. Ключевое решение: создание отдельной тестовой утилиты для экспериментов

**Проблема**: множество параметров (размер чанка, перекрытие, модель эмбеддинга, промпт эмбеддинга, мерность индекса, виды поиска, реранкинг, мультиквери и др.). Изменение параметра требует полного перетестирования.

**Решение**: разработать утилиту (не микросервис, отдельный проект), которая:

- работает с тестовой базой знаний (каталог документов);
- проводит эксперименты с разными параметрами;
- выдает таблицу результатов.
- **Важно**: эту утилиту может делать любой участник (можно объявить на общем собрании), необязательно загонять в микросервисную архитектуру. После отбора лучших идей – интегрировать в микросервисы.

**Договоренность**: использовать для экспериментов локальные LLM и эмбеддинги (обещали видеокарту). Отмечено, что локальные модели могут быть качественнее платных API и поддерживают индексацию по промпту.

## 4. Технические договоренности по развертыванию и тестированию

**Проблема**: сложно проверять коммиты участников на сервере (нет мониторинга, много времени уходит на развертывание и поиск ошибок).

**Решение**: создать локальную среду для быстрого тестирования всей системы.

- Каждый разработчик сервиса должен создать **Dockerfile** для своего сервиса.
- Затем эти Dockerfile будут собраны в общий **docker-compose**, который одной командой поднимает всю инфраструктуру (Postgres 16 + pgvector, MinIO, все сервисы) на любой машине.
- Уже существует утилита **ServiceChecker**, которая пока только пингует сервисы (без БД). Её планируется расширить, чтобы она прогоняла полный сценарий внутри поднятых контейнеров.

**Ответственный**: Игорь обещал подготовить пример docker-compose (со своим RackBuilder + базой) для апробации метода. Затем подход будет рекомендован всем.

## 5. Архитектурное изменение

- **Query-сервис** стал самостоятельным (раньше планировался через оркестратора). У него появился **микропайплайн**: запрос сначала записывается в историю чата, затем извлекается и обрабатывается. Очередь отдельная не нужна.

## 6. Документация и процесс разработки

- Отмечена высокая качество документации от Игоря (четкие API, секвенс-диаграммы, пайплайны, ничего лишнего). Она взята за образец.
- **Лайфхак**: при использовании нейросетей для кодинга (vibe coding) детальная документация служит защитой от деградации – если нейросеть портит код, ей указывают «делай в соответствии с документацией».
- Планируется добавлять во всех сервисах описание логики (на уровне пайплайнов и ключевых вех), но внутренняя реализация остаётся на усмотрение разработчиков.

## 7. Особенности и обсуждённые нюансы

- **Неопределённая часть системы** – регуляторная (поиск по нормативным документам). По ней почти нет исследований, будут делать на ходу.
- Для тестирования рекомендуется использовать **майнинговые видеокарты** (за 3500 руб. с 10 ГБ, но только FP16). Они подходят для индексирования и LLM (не для обучения). Даже есть утилита для снижения энергопотребления до 3–8 Вт.
- Альтернатива – Google Colab, но там лимит 2 часа и неудобный интерфейс.
- Для перебора параметров экспериментов упомянута библиотека **Optuna** (раньше использовалась для подбора параметров фильтров изображения). Её можно попробовать.
- **Python версии 3.13** – стандарт для проекта.

## 8. Непосредственные договорённости на ближайшее время

1. **Игорь**:
   - подготовит пример docker-compose для локального развертывания (RackBuilder + Postgres).
   - выложит утилиту ServiceChecker в backend.
2. **Всем разработчикам сервисов** – необходимо добавить Dockerfile в свои репозитории.
3. **Павел** (или кто из докладчиков) – найти и предоставить ссылку на документ по pipeline (версия 1.4 из первой группы), где описана планируемая архитектура RAG.
4. **Общее собрание** – объявить о создании тестовой утилиты и привлечь желающих для экспериментов с параметрами.

## 9. Открытые вопросы / что осталось

- Отсутствует сервис **конвертер-валидатор** (в процессе разработки).
- Фронтенд пока не интегрирован в тестовую среду (нужно будет решать отдельно).
- Нет единого автотеста, который прогоняет полный сценарий (это в планах расширения ServiceChecker).
