### Технические детали

- **Пайплайн обработки (согласованная схема):**
  
  1. **OCR (Sierra/Parser)** – создаёт цифровой слой из изображения (может быть полным или превью на 3–5 страниц).
  
  2. **Превью-сервис (реализация Павла)** – берёт PDF с цифровым слоем, извлекает PyMuPDF первые страницы, отправляет в LLM (VLM-модель), получает JSON с метаданными (название, коды, издатель, язык и т.п.).
  
  3. **Конвертация (логический парсер, он же чанк-контейнер)** – из полного цифрового слоя собирает иерархическую структуру документа (чанки, списки, таблицы, формулы, блоки графики, внешние ссылки). Целевой формат выхода – JSON с ID документа и версии. Пока не реализован как микросервис, ожидается от Кептилова (Лама-парсер).

- **Архитектура решения Павла (регистратор документов):**
  
  - Толстый клиент на **Python** (GUI – библиотека ClickTime).
  
  - Прямое подключение к **PostgreSQL** и **MinIO**.
  
  - **LLM-промпт**: чётко заданы поля JSON (тип документа, название, коды, издатель, юрисдикция и др.), правила извлечения (не выдумывать, но для некоторых полей разрешена «свобода»). В промпт вшит классификатор «Петробал».
  
  - **Нормализация названия**: приведение к нижнему регистру, удаление лишних пробелов, исправление «аватар» (смесь русских/английских букв), добавление суффиксов через `|` (например, ISO, RF). По нормализованному названию вычисляется **хеш** для дедупликации.
  
  - **Структура БД (ключевые таблицы):**
    
    - `documents` – основная запись (ID, название, коды, метаданные, нормализованное название, хеш имени файла).
    
    - `document_versions` – версии файла (хеш содержимого, ссылка на объект в MinIO: `bucket/document/version/filename`).
  
  - **Дедупликация**: запрет вставки документа с одинаковым хешем нормализованного названия.
  
  - **Удаление**: каскадное удаление записи в БД и файлов в MinIO.

- **Инструменты:** PyMuPDF, LLM/VLM через API (подписка GPT+ и аналоги), PostgreSQL, MinIO, Python, ClickTime, OpenAPI-ключи.

Озвученный алгоритм обработки документов (Purgatory)

### Как работает обработка документов (текущая реализация + планы)

#### Этап 1: Получение цифрового слоя (OCR / парсинг)

- Если документ — скан (изображение), запускается **OCR-сервис** (Sierra / UCR). Он распознаёт текстовый слой, стараясь «выжать максимум» видимых блоков.

- Если документ уже содержит текстовый слой (например, PDF из «Меганормы»), OCR можно не делать или запустить **только превью** (первые 3–5 страниц) для экономии ресурсов.

#### Этап 2: Превью-анализ и извлечение метаданных (сервис Павла)

- Документ открывается через **PyMuPDF**, текст первых 3–5 страниц отправляется в **LLM** со специальным промптом.

- LLM возвращает **JSON** с идентификационной метаинформацией:
  
  - Название документа (не имя файла),
  
  - Коды (НКС, ISO, УДК, классификатор ПКБ и т.д.),
  
  - Издатель и юрисдикция,
  
  - Тип источника (например, «циркулярное письмо»),
  
  - Основной язык.

- Эта информация служит для **уникальной идентификации** документа в базе.

#### Этап 3: Нормализация и дедубликация

- Название приводится к нормализованному виду:
  
  - нижний регистр,
  
  - удаление лишних пробелов,
  
  - исправление замены русских/английских букв,
  
  - добавление кодов через разделители.

- По нормализованному названию строится **хеш-имени-файла**, который гарантирует, что один и тот же документ (даже с разным регистром и пробелами) не будет добавлен повторно.

- Дополнительно хранится **хеш самого файла** (для проверки целостности версии).

#### Этап 4: Сохранение и версионирование

- Документ регистрируется как логическая единица в **PostgreSQL** (таблица документов).

- Файлы версий хранятся в **[Min.io](https://min.io/)** (бакеты «документы» и «версии»). Каждая версия имеет ссылку на [Min.io](https://min.io/) и хеш файла.

- Предполагается, что в будущем можно будет выбирать **наилучшую версию** для дальнейшей обработки.

#### Этап 5: Логический парсер (конвертация) — **в стадии проектирования/прототипа**

- Из уже готового текстового слоя (или результатов парсера) специальный сервис (конвертер, он же «логический парсер») должен собрать **чанк-контейнер** — структурированное представление документа:
  
  - заголовки, пункты, подпункты,
  
  - списки и абзацы,
  
  - таблицы (отдельными блоками),
  
  - формулы (с аннотациями),
  
  - чертежи/изображения (с возможной аннотацией),
  
  - все внешние ссылки на ГОСТы, циркуляры и т.п.

- Именно этот чанк-контейнер будет использоваться поисковым механизмом и аналитикой.

- Ранее был создан прототип такого контейнера (включая граф внешних ссылок и уровни L3), и он рассматривается как целевой ориентир.

---

Таким образом, обработка документа — это конвейер: **OCR → извлечение метаданных (превью) → нормализация/дедубликация → сохранение → логическая конвертация в чанк-контейнер**.  
На встрече детально разбирали именно текущую реализацию Павла (этапы 2–4) и обсуждали, что для полноты картины необходимо доделать этап 5.
