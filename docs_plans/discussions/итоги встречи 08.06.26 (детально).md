### 2. Сервис‑чекер (Service Checker)

**Что это**  
Утилита, которая локально поднимает все сервисы в **одном Docker‑образе**, эмулирует работу инфраструктуры и проверяет работоспособность каждого сервиса (health‑check, а в ближайшее время — прогон полного пайплайна).

**Решения и договорённости**

- **Обязательный инструмент** начиная со следующей недели: перед сдачей каждый запускает чекер, чтобы убедиться, что сервис реально работает.

- Запуск первого раза — через AI‑ассистента (чтобы он установил всё необходимое).

- Код выложен в репозитории, есть README и ритмы (ссылка Диане передана).

**Текущий статус и планы**

- Пока проверяет, что сервисы запускаются и отвечают.

- **Игорь** завтра‑послезавтра (до среды) доделает чекер так, чтобы он **прогонял весь pipeline** и выдавал отчёт об ошибках.

**Нюанс с embedding‑сервисом**

- Чекер собирает все сервисы в один образ через volume, использует свой `requirements.txt`.

- **Виталий** указал, что его сервису нужен `Sentence Transformers` (≈2 ГБ), который отсутствует в сборочном образе чекера.

- Игорь признал, что забыл об этом. Решение: пока **не добавлять** эту зависимость в общий чекер, а сервис эмбеддингов тестировать уже сразу отдельным Docker‑контейнером.

### 3. Файловое хранилище (S3)

**Ключевые решения**

1. **Имя файла = хэш содержимого (SHA‑256)**.
   
   - Гарантирует уникальность.
   
   - Автоматически выявляет дубликаты (система обещает, что коллизий не будет).
   
   - Никаких целочисленных ID, UID или ручных названий для файлов.
   
   **Имя картинки = любая уникальная комбинация**.
   
   - Гарантирует уникальность.
   
   - Можно комбинация ID, номера картинки и т.п.

2. **Глобально только два бакета:**
   
   - `files` – для самих документов.
   
   - `images` – для извлечённых картинок.  
     (Возможно, в будущем появится `tables` или `formulas`, пока только `images`.)

3. **Папки внутри бакетов** – временно оставляются (например, с ID задачи) **только для наглядности**, чтобы без захода в БД видеть, к какому документу относятся файлы. Если станут не нужны — уберутся.

4. **Связь файлов и сущностей** ведётся через PostgreSQL: таблица документов и секций будет содержать ссылки на бакеты.
   
   - Общий компонент для работы с файловым хранилищем будет унифицирован, чтобы как минимум три сервиса работали по единым правилам.

**Уточнение для Дианы**

- Сейчас при парсинге она складывала картинки в бакет `images` в папку с ID задачи.

- Новая логика: в бакет `images` складываем все картинки «кучей», каждая с уникальным именем. Например связка «документ — картинка» — через базу.

### 4. Парсинг и API (превью / полный парсинг)

**Проблема**  
Раньше предполагалось два раздельных вызова: превью (первые страницы) и полный парсинг. Это создавало сложности для парсинга и пайплайна.

**Принятое решение**

- Вместо двух endpoints (`/preview`, `/parse`) остаётся **один** — `parse` с опциональным режимом (`mode=preview` / `mode=full`).

- Сервис‑парсер, если умеет делать превью, возвращает его; если нет — возвращает полный документ, но в метаданных указывает `mode=full`.

- Пайплайн анализирует это поле и не запускает повторный полный парсинг, пропуская этап конвертации.

**План действий**

- **Игорь** уже создал новый API в ветке `docs`, сегодня выложит в `develop`.

- **Диана** после этого обновит свой парсер: подстроит endpoint и условия на выходе.

**Система мониторинга**

- Диана нашла и настроила систему (вместо Grafana), которая **из коробки** собирает:
  
  - структурированные логи,

  - визуализацию потребления ресурсов.

- Система современная, работает без сложной конфигурации, «не трогая заводские настройки».

- Будет выложена инструкция с примерами, чтобы любой мог запустить локально.

- Срок хранения логов — **одна неделя** (в системе по умолчанию так, ничего дописывать не надо).

**Логирование**

- Логи должны быть **структурированными** (в формате, совместимом с OpenTelemetry).

- Уровни — стандартные (`debug`,` info`,` error`,` warning`).

- Диана выложит примеры, как они должны выглядеть.

- Разработчикам на следующей неделе будут выставлены задачи по подключению логов.

**Мониторинг**

- Пока ставится минимальный, на следующей итерации — расширение.

- Задачи будут сформулированы на следующей неделе, но примеры Диана подготовит уже сейчас.

**Актуальность для Андриса**

- Андрису нужно логирование и мониторинг, но Диана подтвердила — это вторая очередь (следующая неделя).

### 7. Классификаторы и база знаний (UI / API)

**Что есть сейчас есть в Purgatory**

- В базе загружены системные классификаторы: **МКС** (полный, ≈1200 записей) и **ОКВЭД‑подобный ПКБ** (≈20 записей).

- Остальных нет в полном объёме (например, УДК — иерархия запутанная, отложено).

- Промпт умеет находить МКС в тексте и отдавать код в JSON.

**Проблема**

- В веб‑интерфейсе не реализован функционал по работе с классификаторами, импорту справочников и загрузке данных (хотя API методы есть).

- Неясно, как будет заноситься справочная информация.

- Для пользовательских категорий (то, что просил Семён) нужна возможность ручной корректировки.

**Решения и план**

1. **Неизвестные коды (pending classifiers)**
   
   - Если классификатор, найденный в документе, отсутствует в базе, он попадает в таблицу `pending_classifier`.
   
   - Администратор получает сигнал и решает: добавить, отклонить или проигнорировать.
   
   - Такой механизм уже спроектирован в микросервисах, но код работы с ним ещё не написан – это нормально для текущего этапа.

2. **UI – вкладка «Метаданные»**
   
   - Во фронтенде уже есть вкладка «Метаданные» с полями для ГОСТ, МКС, УДК и др.
   
   - **Добавить:** (возможно) отображение сырого JSON, который конвертер; статус загрузки документа; информацию об ошибках классификации.
   
   - Сделать возможность ручного редактирования свойств документа (подтверждение, изменение категорий).
   
   - Т.к. заказчик не даёт обратной связи, команда действует по принципу «зафиксируем то, что есть, и дозаполним сами» — эксперименты по заполнению этой вкладки будут продолжены.

3. **Отсутствие кода**
   
   - Если промпт не нашёл ни одного кода, в поле пишется `0` (означает «не классифицирован»).
   
   - Если кодов несколько, пока берётся первый попавшийся (ограничение промпта).

### 8. Сервис эмбеддингов (Infinity)

**Задача**  
Выделенный сервис, который будет обслуживать запросы на эмбеддинги от `RagBuilder` и `RagSearch`, чтобы не встраивать модель в каждый микросервис.

**Технические требования и планы**

- Предварительно выбран **Infinity** — оптимизирован под пакетную обработку, поддерживает 8‑битные эмбеддинги, работает на старых GPU.

- **Виталию** поставлена задача на **следующую неделю**: развернуть и протестировать его.

- Для остальных сервисов это будет просто внешний HTTP‑вызов по `Base URL` (предположительно OpenAI‑совместимый API, но нужно уточнить).

- Ключ/токен не потребуется (локальный сервис).

- Переменные окружения для подключения к БД и другим службам будут задаваться через `docker-compose` на сервере.

**Важный нюанс**  
Сейчас модель эмбеддингов в общем чекере не поднимается из‑за размера зависимостей. Первое полноценное тестирование с embeddings состоится уже отдельным докер контейнером.
