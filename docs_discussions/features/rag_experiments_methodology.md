## 1. Зачем нужны эксперименты

На 03.06.2026 RAG-компоненты (RagBuilder, RagSearch, QueryService) существуют в виде прототипов. Нет данных о том, какие комбинации параметров дают наилучшее качество поиска. Изменение любого параметра требует полного перетестирования. Эксперименты нужны, чтобы **до Спринта 3** (деплой на сервер) зафиксировать оптимальные настройки.

> **Важно:** серверное разворачивание — опционально. Утилита может работать напрямую из Python, импортируя код RagBuilder/RagSearch. PostgreSQL тоже не обязателен — эмбеддинги можно хранить локально (in-memory / файл) без потери качества метрик.

## 2. Что тестируем: полный перечень параметров

### 2.1. Чанкование (RagBuilder)

Параметры из API `POST /rag/build` (`options.strategy` и производные):

| Параметр                 | Значения для тестирования                                     | Источник                            |
| ------------------------ | ------------------------------------------------------------- | ----------------------------------- |
| **Стратегия чанкования** | `semantic_512`, `fixed_256`, `fixed_512`, `fixed_1024`        | `options.strategy` в RagBuilder API |
| **Overlap (перекрытие)** | 0%, 10%, 25%, 50% от размера чанка                            | Производный (в коде чанкера)        |
| **Protected spans**      | Без разделённых диапазонов / с защищёнными (таблицы, формулы) | `protected_spans` в запросе         |
| **Обработка таблиц**     | Только markdown / columns+rows+markdown / только сырые данные | Стратегия `table` → чанк            |
| **Обработка формул**     | latex + meaning / только latex / только meaning               | Стратегия `formula` → чанк          |

> **Примечание**: `semantic_512` — разбиение по семантическим границам с максимумом 512 токенов на чанк. `fixed_N` — жёсткое разбиение по N токенов.

### 2.2. Модели эмбеддингов

| Модель                                          | Размерность (max) | VRAM (int8) | VRAM (FP16) | MRL | Источник                   |
| ----------------------------------------------- | ----------------- | ----------- | ----------- | --- | -------------------------- |
| `Qwen/Qwen3-Embedding-4B`                       | 2560              | ~4 ГБ       | ~8 ГБ       | Да  | План (п. 4.8)              |
| `Qwen/Qwen3-Embedding-8B`                       | 4096              | ~8 ГБ       | ~16 ГБ      | Да  | План (п. 4.8)              |
| `intfloat/multilingual-e5-large`                | 1024              | —           | ~2.2 ГБ     | Нет | Альтернатива               |
| `BAAI/bge-m3`                                   | 1024              | —           | ~2.2 ГБ     | Нет | Альтернатива               |
| `paraphrase-multilingual-MiniLM-L12-v2`         | 384               | —           | ~0.5 ГБ     | Нет | Лёгкая (бюджетный вариант) |

> **MRL (Matryoshka Representation Learning)** — возможность усекать размерность эмбеддинга без переобучения. Поддерживается **только Qwen3-Embedding**. У остальных моделей (e5-large, bge-m3, MiniLM) размерность фиксированная, варьировать нечего.
>
> **Сетка тестируемых размерностей:**
> - Qwen3-Embedding-4B: `2560 / 2048 / 1536` (максимум 2560)
> - Qwen3-Embedding-8B: `4096 / 2048 / 1536` (максимум 4096)
>
> **Цель**: проверить, насколько 4000+ мерностей превосходят 2000 и 1500 — чтобы не перегружать индексы в БД. Если разница < 1–2%, фиксируем 2048.
>
> **Битность**: для продакшена планируется int8-квантование (4B → ~4 ГБ, 8B → ~8 ГБ). Подробнее — в §2.8.

### 2.3. Промпт эмбеддинга (instruction prefix)

| Вариант                | Шаблон                                                     |
| ---------------------- | ---------------------------------------------------------- |
| **Без промпта**        | `{text}`                                                   |
| **query-промпт**       | `query: {text}`                                            |
| **passage-промпт**     | `passage: {text}`                                          |
| **Раздельные промпты** | Для запроса: `query: {text}`, для чанка: `passage: {text}` |
| **E5-стиль**           | `query: {text}` / `passage: {text}`                        |

### 2.4. Типы поиска (RagSearch)

| Параметр        | Значения                                                                                                                        | API-поле                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| **Тип поиска**  | `dense` (только векторный), `sparse` (только BM25/pg_trgm), `hybrid` (простое слияние dense+sparse), `hybrid_rrf` (RRF-слияние) | `search_type` + константы  |
| **RRF k**       | 10, 30, 60 (default), 100, 200                                                                                                  | Константа в коде RagSearch |
| **top_k**       | 3, 5, 10, 15, 20                                                                                                                | `top_k`                    |
| **Реранкинг**   | `false`, `true` (cross-encoder)                                                                                                 | `rerank`                   |
| **Мультиквери** | `false`, `true` (авто-декомпозиция запроса на подзапросы)                                                                       | `options.auto_decompose`   |

> **Важно**: различаем **Hybrid** (простое слияние: среднее/взвешенное оценок dense и sparse) и **Hybrid_RRF** (Reciprocal Rank Fusion: `score = Σ 1/(k + rank_i)`). Это разные стратегии, и по предварительным данным Hybrid_RRF значимо лучше простого Hybrid (p=0.0000).

### 2.5. 9 тестируемых стратегий поиска (полный перечень)

На основе предварительных статистических тестов (см. §2.7) определены 9 стратегий, которые сравниваются попарно:

| #   | Стратегия                    | Состав                                               |
| --- | ---------------------------- | ---------------------------------------------------- |
| S1  | **Vector**                   | Только dense (векторный поиск)                       |
| S2  | **Vector+Rerank**            | Dense + cross-encoder реранкинг                      |
| S3  | **BM25**                     | Только sparse (полнотекстовый BM25/pg_trgm)          |
| S4  | **Hybrid**                   | Dense + sparse, простое слияние (среднее/взвешенное) |
| S5  | **Hybrid+Rerank**            | S4 + cross-encoder реранкинг                         |
| S6  | **Hybrid_RRF**               | Dense + sparse, слияние через RRF (k=60)             |
| S7  | **Hybrid_RRF+Rerank**        | S6 + cross-encoder реранкинг                         |
| S8  | **Hybrid+MultiQuery**        | S4 + авто-декомпозиция запроса на подзапросы         |
| S9  | **Hybrid+MultiQuery+Rerank** | S8 + cross-encoder реранкинг                         |

#### 2.7.2. Попарные сравнения (пример)

**Легенда**: ✓ = значимое различие (p < 0.05), ✗ = не значимо (p ≥ 0.05).

| Сравнение                                     | p-value    | Значимо? | Вывод                                                        |
| --------------------------------------------- | ---------- | -------- | ------------------------------------------------------------ |
| Vector vs Vector+Rerank                       | 0.0702     | ✗        | Реранкинг без hybrid не даёт прироста                        |
| Vector vs BM25                                | 0.0001     | ✓        | BM25 значимо лучше чистого вектора                           |
| Vector vs Hybrid                              | 0.0000     | ✓        | Hybrid значимо лучше вектора                                 |
| Vector vs Hybrid_RRF                          | 0.0001     | ✓        | Hybrid_RRF значимо лучше вектора                             |
| Vector vs Hybrid+MultiQuery                   | 0.0000     | ✓        | Hybrid+MultiQuery значимо лучше вектора                      |
| Vector vs Hybrid+MultiQuery+Rerank            | 0.0000     | ✓        |                                                              |
| **BM25 vs Hybrid_RRF**                        | **nan**    | **✗**    | **BM25 сравним с Hybrid_RRF** (нет значимого различия)       |
| Hybrid vs Hybrid_RRF                          | 0.0000     | ✓        | RRF-слияние значимо лучше простого                           |
| Hybrid vs Hybrid+MultiQuery                   | 0.0042     | ✓        | Мультиквери значимо лучше простого Hybrid                    |
| **Hybrid vs Hybrid+MultiQuery+Rerank**        | **0.0772** | **✗**    | Добавление мультиквери+реранка к Hybrid — не значимо         |
| **Hybrid+Rerank vs Hybrid+MultiQuery+Rerank** | **0.1158** | **✗**    | Мультиквери не добавляет значимости, если уже есть реранкинг |
| Hybrid_RRF vs Hybrid_RRF+Rerank               | 0.0283     | ✓        | Реранкинг улучшает Hybrid_RRF                                |
| Hybrid_RRF vs Hybrid+MultiQuery               | 0.0000     | ✓        |                                                              |
| Hybrid+MultiQuery vs Hybrid+MultiQuery+Rerank | 0.0002     | ✓        | Реранкинг улучшает Hybrid+MultiQuery                         |

**Ключевые выводы для планирования экспериментов:**

1. **Vector+Rerank (S2) может не давать прироста** — реранкинг без гибридного слияния. Проверяем на наших данных.
2. **BM25 (S3) сравним с Hybrid_RRF (S6)** — p=nan (вероятно, идентичные/близкие результаты). BM25 — сильный baseline, обязательно тестируем.
3. **Hybrid_RRF (S6) значимо лучше простого Hybrid (S4)** — RRF-слияние обязательно.
4. **Hybrid+MultiQuery+Rerank (S9) не значимо лучше Hybrid+Rerank (S5)** — мультиквери не добавляет ценности поверх реранкинга. Но S9 значимо лучше S8 (без реранка).
5. **Фокус на S5 (Hybrid+Rerank), S7 (Hybrid_RRF+Rerank), S9 (Hybrid+MultiQuery+Rerank)** — три топ-стратегии с реранкингом.

### 2.8. Инфраструктура эмбеддингов

> **Все компоненты инфраструктуры — опциональны.** PostgreSQL и Infinity-сервер не требуются для экспериментов: утилита умеет работать напрямую из Python с локальным хранением эмбеддингов. Серверный режим тестируется отдельно (Фаза 3) для оценки продакшен-накладных расходов.

| Параметр                        | Значения                                                                       |
| ------------------------------- | ------------------------------------------------------------------------------ |
| **Режим**                       | Локальная загрузка модели в Python / Infinity-сервер                           |
| **Infinity**                    | Docker Linux, персистентное хранилище, OpenAI-совместимый API                  |
| **Batch size** (для индексации) | 1, 8, 16, 32                                                                   |
| **GPU**                         | CPU-only / GPU (FP16)                                                          |
| **Битность (квантование)**      | `FP16` (стандарт), `int8` (цель для продакшена)                                |
| **Способ загрузки int8**        | `bitsandbytes` (Python) / Infinity-сервер в докере (обрабатывает битности сам) |
| **VRAM (int8)**                 | Qwen3-Embedding-4B: ~4 ГБ · Qwen3-Embedding-8B: ~8 ГБ                         |
| **Хранение эмбеддингов**        | PostgreSQL+pgvector / In-memory (dict) / Файл (numpy/pt)                       |

**Важно про загрузку int8:** стандартный `sentence-transformers` даже скачав 8-битные веса, загрузит их в память как FP16. Для реального int8 нужен `bitsandbytes` или Infinity-сервер. Infinity битности умеет обрабатывать сам, без дополнительных библиотек. Это будет проверено на отладке Фазы 1.

**Почему не Ollama:** Ollama даёт значительный оверхед на запуск и последовательную обработку, не поддерживает batch-индексацию и несовместима с Infinity-форматом эндпоинтов. Для экспериментов и продакшена она непригодна.

## 4. Метрики оценки (кратко)

> **Полный перечень** метрик, формул, протокола стат. значимости и методики ручной оценки ответов LLM — в **[Методике оценки качества](rag_evaluation_methodology.md)**.

### 4.1. Основные метрики качества поиска

| Метрика                        | Формула / Описание                                            | Целевое значение |
| ------------------------------ | ------------------------------------------------------------- | ---------------- |
| **Precision@5**                | Доля релевантных чанков в топ-5 результатов                   | ≥ 0.70           |
| **Recall@5**                   | Доля найденных релевантных чанков от общего числа релевантных | ≥ 0.60           |
| **MRR** (Mean Reciprocal Rank) | Средний обратный ранг первого релевантного результата         | ≥ 0.75           |
| **NDCG@5**                     | Normalized Discounted Cumulative Gain                         | ≥ 0.70           |
| **Hit@5**                      | Доля запросов, где хотя бы один релевантный чанк в топ-5      | ≥ 0.90           |

### 4.2. Метрики производительности

| Метрика                          | Описание                                              | Приемлемый порог                |
| -------------------------------- | ----------------------------------------------------- | ------------------------------- |
| **Время индексации** (на 1 док.) | От подачи JSON до `status: completed`                 | ≤ 60 сек (CPU) / ≤ 15 сек (GPU) |
| **Время поиска**                 | От отправки запроса до получения топ-10               | ≤ 500 мс                        |
| **Размер индекса**               | Объём `rag_document_chunks` в БД (строки + embedding) | Мониторинг, без порога          |
| **Память модели**                | VRAM / RAM, потребляемая эмбеддинг-моделью            | ≤ доступной памяти              |

### 4.3. Как считать релевантность

Для каждого эталонного вопроса вручную определить:

- `relevant_chunk_ids` — список ID чанков (или section_id+page), которые содержат ответ
- Это делается **один раз** при формировании эталонной базы

Затем для каждого run-а эксперимента:

1. Выполнить поиск → получить ранжированный список результатов
2. Для каждого результата проверить: входит ли `chunk_id` в `relevant_chunk_ids`
3. Рассчитать метрики по всем 35 вопросам

### 6.3. Псевдокод утилиты

```python
# run_experiments.py (псевдокод)
import itertools
import csv
from rag_builder import chunk_and_index    # прямой вызов или через API
from rag_search import search              # прямой вызов или через API
from metrics import precision_at_k, recall_at_k, mrr, ndcg

def run_experiment(config):
    # 1. Загружаем эталонные данные
    documents = load_documents(config["ground_truth"]["documents_dir"])
    questions = load_questions(config["ground_truth"]["questions_file"])
    relevance = load_relevance(config["ground_truth"]["relevance_file"])

    # 2. Генерируем сетку параметров (уникальные комбинации индексации)
    #    Индекс строится 1 раз на связку (chunk + overlap + model + dim)
    #    и переиспользуется всеми стратегиями поиска — уникальных индексаций
    #    выходит десятки, а не тысячи.
    grid = list(itertools.product(*config["parameter_grid"].values()))
    # Группируем по уникальным комбинациям индексации
    index_groups = group_by_index_key(grid)

    # Кеш индексов: index_key → index_stats
    index_cache = {}

    results = []
    for params in grid:
        index_key = (params.chunk_strategy, params.chunk_overlap, 
                     params.embedding_model, params.dim)

        # 3. Индексация — только если ещё не построена
        if index_key not in index_cache:
            index_stats = chunk_and_index(
                documents, 
                strategy=params.chunk_strategy,
                overlap=params.chunk_overlap,
                model=params.embedding_model,
                dim=params.dim,             # усечение размерности (MRL)
                quantization=params.quantization  # fp16 / int8
            )
            index_cache[index_key] = index_stats
        else:
            index_stats = index_cache[index_key]

        # 4. Поиск по всем вопросам
        #    Эмбеддинги запроса считаются на каждый поисковый ран:
        #    embed, rerank (cross-encoder), bm25, multiquery.
        metrics_sum = defaultdict(float)
        for q in questions:
            search_results = search(
                q.text,
                search_type=params.search_type,
                top_k=params.top_k,
                rerank=params.rerank
            )
            # 5. Сравниваем с эталоном
            relevant_ids = relevance[q.id]
            metrics_sum["precision@5"] += precision_at_k(search_results, relevant_ids, k=5)
            metrics_sum["recall@5"] += recall_at_k(search_results, relevant_ids, k=5)
            metrics_sum["mrr"] += mrr(search_results, relevant_ids)

        # 6. Усредняем метрики
        n = len(questions)
        results.append({
            **params._asdict(),
            "precision@5": metrics_sum["precision@5"] / n,
            "recall@5": metrics_sum["recall@5"] / n,
            "mrr": metrics_sum["mrr"] / n,
            "index_time_sec": index_stats["processing_time_sec"],
            "chunks_count": index_stats["chunks_count"]
        })
        # НЕТ cleanup_index() — индекс переиспользуется между поисковыми ранами

    # 8. Сохраняем результаты
    save_results(results, config["output"]["path"])
```

## 9. Критерии выбора финальной конфигурации

Приоритет метрик (по убыванию важности):

1. **MRR** — пользователь должен видеть правильный ответ первым
2. **Recall@5** — все релевантные чанки должны быть в топ-5
3. **Precision@5** — минимум мусора в выдаче
4. **Время поиска** — ≤ 500 мс для комфортной работы
5. **Время индексации** — приемлемо до 60 сек на документ

**Формула сводного скора:**

```
Score = 0.35 × MRR + 0.25 × Recall@5 + 0.15 × Precision@5 + 0.10 × Hit@5 
      − 0.10 × norm(search_time) − 0.05 × norm(index_time)
```
