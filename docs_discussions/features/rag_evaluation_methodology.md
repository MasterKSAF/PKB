## 1. Как составить качественный набор эталонных запросов

### 1.1. Принципы отбора запросов

Плохой набор запросов — главная причина неверных выводов эксперимента. Запросы должны:

1. **Покрывать разнообразие** — разные типы вопросов, разные типы секций документа
2. **Иметь однозначный эталонный ответ** — эксперт должен точно знать, где ответ и как он выглядит
3. **Быть реалистичными** — похожи на то, что спросит реальный инженер ПКБ
4. **Иметь разную сложность** — от тривиального поиска по ключевым словам до требующих логического вывода

### 1.2. Типология запросов (5 категорий)

| Категория | Пример | Что проверяет | Ожидаемая сложность |
|-----------|--------|---------------|---------------------|
| **A. Фактографический** (точное значение) | «Какая минимальная толщина обшивки для ледового класса Arc4?» | Поиск точного значения в ячейке таблицы или абзаце | Низкая |
| **B. Интерпретационный** (соответствие требованию) | «Соответствует ли толщина обшивки 14 мм требованиям для Arc4?» | Поиск параметра + сравнение с порогом | Средняя |
| **C. Составной** (несколько фактов) | «Какие требования к соосности и перпендикулярности для стоек нормальной точности?» | Поиск нескольких чанков, агрегация | Средняя |
| **D. Определительный** (термин/понятие) | «Что такое установочная крепежная стойка по ГОСТ 20868-81?» | Поиск определения термина, cross-reference | Низкая–средняя |
| **E. Сравнительный** (между документами) | «Чем отличаются требования к точности в ГОСТ 20868-81 и ГОСТ 24705-2004?» | Поиск в нескольких документах, сравнение | Высокая |

**Рекомендуемое распределение** на 35 запросов:

| Категория | Кол-во | % |
|-----------|--------|---|
| A (фактография) | 10 | 29% |
| B (интерпретация) | 8 | 23% |
| C (составные) | 8 | 23% |
| D (определения) | 5 | 14% |
| E (сравнительные) | 4 | 11% |

### 1.3. Требования к формулировке запроса

- Запрос — **на естественном языке**, так как спросил бы инженер (не «толщина обшивки Arc4», а «Какая должна быть толщина обшивки для ледового класса Arc4?»)
- **Один вопрос — один запрос**. Не «расскажи про допуски и про толщину».
- Содержит достаточно контекста для однозначного ответа (класс точности, эпоха документа, тип изделия)
- Для категорий B и E — включает **условие** («соответствует ли», «отличаются ли»)

### 1.4. Покрытие типов контента

Каждый запрос должен быть привязан к определённому типу секции-источника ответа:

| Тип секции | Мин. кол-во запросов | Пример запроса |
|------------|---------------------|----------------|
| `text` (сплошной текст) | 8 | «На какие изделия распространяется ГОСТ 20868-81?» |
| `table` (таблица) | 8 | «Какой допуск соосности для L от 6 до 50 мм при нормальной точности?» |
| `list` (перечень) | 3 | «Перечисли допуски для стоек нормальной точности» |
| `formula` (формула) | 3 | «По какой формуле рассчитывается допустимый радиус соосности?» |
| `image` (чертёж/схема) | 2 | «Что изображено на чертеже 1 в ГОСТ 20868-81?» |
| Смешанный (текст + таблица) | 6 | «Какие требования к соосности и как они зависят от L?» |
| Меж-документный | 5 | «Отличаются ли допуски в ГОСТ 20868-81 от ГОСТ 24705-2004?» |

## 2. Как формировать эталонные ответы (ground truth)

### 2.1. Три уровня разметки

Для каждого запроса формируется эталон на трёх уровнях:

| Уровень | Что содержит | Для каких метрик |
|---------|-------------|-----------------|
| **L1: Секции-источники** | `document_code`, `clause`, `page` — где находится ответ | Recall (на уровне секций) |
| **L2: Идеальные чанки** | `chunk_id` (после индексации) — какие чанки содержат ответ | Precision@k, Recall@k, MRR |
| **L3: Степень релевантности** | Оценка 0–3 для каждого чанка в топ-выдаче | NDCG, взвешенные метрики |

### 2.2. Шкала релевантности чанка (L3)

Не бинарно «релевантен / не релевантен», а по степеням:

| Оценка | Определение | Пример |
|--------|------------|--------|
| **3 — Идеальный** | Чанк содержит полный и точный ответ на вопрос | Ячейка таблицы с нужным значением допуска |
| **2 — Высокий** | Чанк содержит существенную часть ответа, но не полный | Абзац с требованиями, но без конкретных цифр |
| **1 — Связанный** | Чанк тематически связан, но не отвечает на вопрос | Соседний пункт того же раздела |
| **0 — Не релевантен** | Чанк не относится к вопросу | Фрагмент из другого документа |

### 2.3. Процесс разметки L1 (секции-источники)

Выполняется **до индексации**, экспертом-предметником (Полина / Семён):

1. Для каждого вопроса прочитать документы и найти секции, содержащие ответ
2. Заполнить карточку:
   ```json
   {
     "question_id": "Q001",
     "text": "Какая минимальная толщина обшивки для ледового класса Arc4?",
     "category": "A",
     "source_sections": [
       {"document_code": "ГОСТ Р 58774-2019", "clause": "4.2", "page": 42}
     ],
     "expected_answer_summary": "не менее 12 мм",
     "notes": "Значение в таблице 4.2, столбец 'Толщина, мм', строка 'Arc4'"
   }
   ```

### 2.4. Процесс разметки L2 и L3 (чанки и релевантность)

Выполняется **после первой индексации** эталонного набора документов:

1. Запустить индексацию эталонных документов с базовыми параметрами
2. Для каждого вопроса выполнить поиск с заведомо большим `top_k=50`
3. Эксперт (НЕ разработчик!) просматривает топ-50 чанков и для каждого выставляет оценку 0–3
4. `chunk_id` с оценкой 2 или 3 формируют `relevant_chunk_ids` для автоматических метрик
5. Результат сохраняется как **единый файл разметки**, используемый всеми run'ами

**Важно**: разметку делает эксперт предметной области, а не разработчик поиска — чтобы избежать bias'а.

### 2.5. Формат единого файла разметки

```json
{
  "metadata": {
    "created_at": "2026-06-07",
    "documents_count": 10,
    "questions_count": 35,
    "annotator": "Полина",
    "indexing_params_snapshot": {
      "strategy": "semantic_512",
      "model": "Qwen/Qwen2.5-4B-Instruct"
    }
  },
  "questions": [
    {
      "question_id": "Q001",
      "text": "Какая минимальная толщина обшивки для ледового класса Arc4?",
      "category": "A",
      "source_sections": [
        {"document_code": "ГОСТ Р 58774-2019", "clause": "4.2", "page": 42}
      ],
      "expected_answer_summary": "не менее 12 мм",
      "relevant_chunks": [
        {"chunk_id": 128, "relevance": 3},
        {"chunk_id": 127, "relevance": 1}
      ],
      "all_judged_chunks": {
        "128": 3, "127": 1, "125": 0, "200": 0, "55": 0
      }
    }
  ]
}
```

## 3. Метрики: полный перечень

### 3.1. Автоматические метрики (считаются скриптом)

| Метрика | Формула | Что измеряет | Мин. приемлемо | Цель |
|---------|---------|-------------|---------------|------|
| **Precision@5** | `|relevant ∩ top5| / 5` | Доля релевантных в топ-5 | 0.50 | 0.70 |
| **Recall@5** | `|relevant ∩ top5| / |all_relevant|` | Полнота в топ-5 | 0.40 | 0.60 |
| **MRR** | `1/N Σ 1/rank_first_relevant` | Как быстро находится первый релевантный | 0.50 | 0.75 |
| **NDCG@5** | `DCG@5 / IDCG@5` | Качество ранжирования с учётом степеней релевантности | 0.50 | 0.70 |
| **Hit@5** | `доля запросов с ≥1 релевантным в топ-5` | Есть ли хоть что-то релевантное | 0.70 | 0.90 |
| **MeanAvgPrecision (MAP)** | `1/N Σ AP_i` | Средняя точность по всем запросам | 0.40 | 0.65 |

### 3.2. Ручные метрики (оцениваются экспертом)

Эти метрики оценивают **качество конечного ответа** (после LLM-генерации), а не только качество поиска:

| Метрика | Шкала | Что измеряет |
|---------|-------|-------------|
| **Полнота ответа** | 1–5 | Все ли аспекты вопроса покрыты? |
| **Фактическая точность** | 1–5 | Нет ли ошибок/галлюцинаций в ответе? |
| **Цитируемость** | 1–5 | Все ли утверждения подкреплены ссылками на источники? |
| **Лаконичность** | 1–5 | Нет ли воды, ответ по существу? |
| **Общая полезность** | 1–5 | Готов ли эксперт использовать этот ответ в работе? |

**Когда применять**: только после выбора топ-3 стратегий поиска (S5, S7, S9) — прогнать их через полный пайплайн с LLM и оценить ответы вручную.

### 3.3. Интегральная оценка стратегии

Для итогового сравнения стратегий используется взвешенный score:

```
Score = 0.25 x MRR + 0.20 x Recall@5 + 0.15 x NDCG@5 + 0.15 x Precision@5 
      + 0.10 x Hit@5 + 0.10 x MAP - 0.05 x norm(search_time_ms)
```

Для финального сравнения (топ-3 стратегии + LLM) — добавляются ручные метрики:

```
FinalScore = 0.6 x Score + 0.4 x (avg_fullness + avg_accuracy + avg_citability) / 3
```

## 4. Протокол проверки значимости различий

### 4.1. Почему недостаточно сравнить средние

Две стратегии могут показать близкие средние MRR, но различие может быть статистически значимым (или наоборот). Нужен формальный тест.

### 4.2. Рекомендуемый метод: парный t-test / Wilcoxon

Для каждого из 35 запросов у нас есть MRR (или другая метрика) для стратегии A и стратегии B. Сравниваем попарно:

```
H0: MRR_A = MRR_B (нет различий)
H1: MRR_A != MRR_B (есть различия)
```

**Если распределение нормальное** (проверить Шапиро-Уилком) → **парный t-test**  
**Если распределение не нормальное** → **Wilcoxon signed-rank test**

Уровень значимости: **α = 0.05** (стандарт).

### 4.3. Поправка на множественные сравнения

При сравнении 9 стратегий попарно получается C(9,2) = 36 сравнений. При α=0.05 ожидается 36 × 0.05 ≈ 2 ложноположительных результата.

**Решение**: применять **поправку Бонферрони** (α / 36 ≈ 0.0014) или **Holm-Bonferroni** (менее консервативная).

### 4.4. Код для автоматического анализа

```python
from scipy.stats import ttest_rel, wilcoxon
import pandas as pd

def compare_strategies(results_csv, strategy_a, strategy_b, metric='mrr'):
    """
    results_csv: CSV с колонками [question_id, strategy, metric]
    Возвращает: p-value, значимо ли различие, средние значения
    """
    df = pd.read_csv(results_csv)
    a = df[df.strategy == strategy_a].set_index('question_id')[metric]
    b = df[df.strategy == strategy_b].set_index('question_id')[metric]
    
    # Убираем запросы, где обе стратегии дали одинаковый результат
    common = a.index.intersection(b.index)
    a, b = a[common], b[common]
    
    # t-test
    t_stat, p_ttest = ttest_rel(a, b)
    # Wilcoxon (непараметрический)
    w_stat, p_wilcoxon = wilcoxon(a, b)
    
    p_value = p_wilcoxon  # более безопасный
    significant = p_value < 0.05
    
    return {
        'strategy_a': strategy_a, 'strategy_b': strategy_b,
        'mean_a': a.mean(), 'mean_b': b.mean(),
        'delta': b.mean() - a.mean(),
        'p_value': p_value, 'significant': significant,
        'test': 'wilcoxon'
    }
```

## 5. Минимальные требования к эталонному набору

Без соблюдения этих требований результаты экспериментов недостоверны:

| Требование | Порог | Почему важно |
|------------|-------|-------------|
| Мин. количество запросов | **30** | Меньше — статистическая мощность тестов падает, p-value становятся неинформативны |
| Мин. количество документов | **5** | Меньше — поиск вырождается, все чанки из одного документа |
| Разные типы секций-источников | **≥3** из 5 (text, table, list, formula, image) | Иначе тестируем только один вид контента |
| Разные категории сложности | **≥4** из 5 (A, B, C, D, E) | Иначе метрики не отражают реальную работу системы |
| Эксперт-разметчик ≠ разработчик | **Обязательно** | Разработчик неосознанно подгоняет разметку под «свою» стратегию |
| Слепая разметка L3 | **Желательно** | Эксперт не должен знать, какая стратегия сгенерировала выдачу |

## 6. Типичные ошибки при оценке качества (как избежать)

| Ошибка | Пример | Как избежать |
|--------|--------|-------------|
| **Слишком лёгкие запросы** | «Что такое ГОСТ 20868-81?» (ответ в заголовке) | Проверить: находит ли BM25 ответ в топ-1? Если да — запрос слишком лёгкий |
| **Слишком сложные запросы** | «Разработай техпроцесс...» (требует рассуждений, не поиска) | Ограничить запросы вопросом «где в документе сказано про X?» |
| **Неоднозначный эталон** | «Какие требования к точности?» (в документе их десятки) | Сузить: «...для стоек нормальной точности по ГОСТ 20868-81» |
| **Разметка «на глаз»** | Эксперт помнит, что «где-то тут было», но не проверяет | Каждый `chunk_id` вручную открыть и прочитать содержание |
| **Мало запросов на таблицы** | Все 35 вопросов — по сплошному тексту | Принудительно выделить 8+ вопросов, где ответ в таблице |
| **Нет отрицательных примеров** | Все запросы имеют ответ в документах | Добавить 3–5 запросов, ответа на которые **нет** в эталонной базе |
