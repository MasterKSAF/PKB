# UI Final: план закрытия API/UX gap после встречи 09.06.2026

Дата: 09.06.2026

## Контекст

План подготовлен по двум источникам:

- memo встречи от 09.06.2026 по разбору интерфейса и ассистента;
- gap-аудит `api_ui_gap_report_2026-06-09.md`.

Цель правок: аккуратно привести UI Final к актуальным Gateway/API-контрактам и решениям встречи, не ломая уже собранную визуальную структуру интерфейса.

Главный принцип: сначала стабилизировать API-слой и режимы данных, затем подключать экраны точечно. Не переписывать интерфейс целиком.

## Главный вывод

UI уже визуально близко подошел к нужной структуре, но самый опасный gap не в дизайне, а в том, что часть сценариев пока имитируется локально вместо работы по Gateway API.

Критичный участок — вкладка "Обработка базы знаний". Сейчас черновики, preview, approve/reject и удаление во многом живут в React-состоянии. По свежей Gateway-документации внешний пользовательский поток должен идти через `/drafts/*`:

1. `POST /drafts` — загрузка файла и создание черновика.
2. `POST /drafts/{draft_id}/preview` — запуск preview.
3. `GET /drafts/{draft_id}/preview/status?longpoll=15` — ожидание preview.
4. `PATCH /drafts/{draft_id}/decide` — approve/reject.
5. `DELETE /drafts/{draft_id}` — soft delete черновика.

`task_id` остается связанным/internal идентификатором. Внешний UI должен работать через `draft_id`.

## Критичные разрывы

### 1. Обработка базы знаний

Что сейчас:

- черновики создаются локально через `setDrafts`;
- файл отправляется через `documentsApi.upload(file)`;
- preview имитируется через `setTimeout`;
- approve/reject меняют локальный статус;
- удаление черновика локальное;
- список черновиков не берется из Gateway.

Что должно быть:

- создание черновика через `POST /drafts`;
- запуск preview через `POST /drafts/{draft_id}/preview`;
- ожидание результата через `GET /drafts/{draft_id}/preview/status?longpoll=15`;
- принятие решения через `PATCH /drafts/{draft_id}/decide`;
- удаление через `DELETE /drafts/{draft_id}`;
- хранение `draft_id`, `task_id`, `document_key`, `document_id`, статуса и preview-метаданных из Gateway.

### 2. Метаданные

Что сейчас:

- форма метаданных есть в UI;
- при upload фактически уходит только файл.

Что должно быть:

- `source_type` отправляется обязательно;
- опциональные поля реально попадают в payload: `title`, `doc_code`, `mks_oks_code`, `okstu_code`, `era`, `jurisdiction`, `issuing_body`, `metadata`;
- блок метаданных остается свернутым по умолчанию;
- после preview UI показывает metadata, извлеченные Gateway;
- пользовательские metadata не должны быть декоративными.

### 3. Demo/Gateway режимы

Что сейчас:

- в Gateway-режиме часть методов при ошибке молча возвращает mock-данные.

Что должно быть:

- demo/mock работает только в demo-режиме;
- Gateway-режим при ошибке показывает ошибку, empty state или offline-состояние;
- UI не должен незаметно подменять реальные данные демонстрационными.

### 4. Чат и longpoll

Что сейчас:

- UI отправляет `POST /chat/sessions/{id}/messages`;
- затем запрашивает всю сессию через `GET /chat/sessions/{id}`;
- longpoll конкретного сообщения не используется.

Что должно быть:

- после отправки сохранять `message_id`;
- ждать результат через `GET /chat/sessions/{session_id}/messages/{message_id}?longpoll=15`;
- обрабатывать документированную FSM longpoll-статусов: `pending`, `enriching`, `searching`, `generating`, `enriching_citations`, `answered`, `failed`;
- не вводить параллельные UI-статусы вместо документированной FSM longpoll.

### 5. База знаний

Что уже близко:

- на главном экране есть статусные карточки;
- разделы базы знаний кликабельны;
- есть провал внутрь раздела;
- внутри раздела есть список документов и preview.

Что нужно поправить:

- убрать локальную привязку документов к разделам;
- фильтровать документы по реальным полям Gateway/Registry;
- для выбранного документа подтягивать detail/status/history/errors/parameters/pages по API;
- не показывать документы на главной странице базы знаний.

### 6. Администрирование, артефакты, журналы

Что сейчас:

- есть административные карточки и часть данных из `admin/audit`;
- полноценные pipeline artifacts/logs пока не подключены.

Что нужно:

- убрать "Документы" и "OCR" как дубли "Обработки базы знаний";
- оставить "Артефакты" и "Журналы" как системные подпункты;
- не строить полноценный экран артефактов до подтверждения backend-контракта;
- уточнить источник данных: `draft.raw_data`, `document pages`, `parameters`, `errors`, `history`, task status или отдельный endpoint.

## Пошаговый план внедрения

### Шаг 1. Подготовить безопасную рабочую ветку

1. Обновить актуальную целевую ветку.
2. Создать отдельную UI-only ветку.
3. Зафиксировать baseline:
   - `npm run lint`;
   - `npm run build`;
   - smoke UI на локальном порту `3300`.
4. Не захватывать незакоммиченные backend/gateway-доки, логи и чужие изменения.

Критерий готовности: есть чистая точка старта, понятно, какие файлы будут меняться.

### Шаг 2. Развести demo и Gateway режимы

1. В `frontend/src/utils/http.ts` убрать silent fallback на mock в Gateway-режиме.
2. Оставить mock только при `workMode === 'demo'`.
3. Для Gateway-ошибок возвращать управляемые ошибки/empty state.
4. Обновить компоненты, чтобы они показывали:
   - "Gateway недоступен";
   - "Нет данных";
   - "Недостаточно прав";
   - "Ошибка загрузки".

Критерий готовности: в Gateway-режиме UI не показывает demo-данные при падении API.

### Шаг 3. Сделать `draftsApi`

Добавить в `frontend/src/utils/http.ts` отдельный адаптер:

- `draftsApi.create(file, metadata, idempotencyKey)`;
- `draftsApi.list(params)`;
- `draftsApi.get(draftId)`;
- `draftsApi.getPreview(draftId)`;
- `draftsApi.startPreview(draftId)`;
- `draftsApi.waitPreview(draftId, longpoll = 15)`;
- `draftsApi.decide(draftId, action, comment)`;
- `draftsApi.delete(draftId)`.

Особенности:

- `POST /drafts` отправляет `multipart/form-data`;
- `source_type` обязателен;
- `metadata` передается JSON-строкой;
- `Idempotency-Key` генерируется на попытку upload;
- `draft_id` становится главным внешним ID черновика.

Критерий готовности: API-слой умеет выполнить полный draft lifecycle без UI-логики.

### Шаг 4. Переподключить "Обработку базы знаний" к drafts API

Файл: `frontend/src/components/KnowledgeProcessing.tsx`.

1. Заменить upload через `documentsApi.upload(file)` на `draftsApi.create(...)`.
2. При создании черновика сохранять:
   - `draft_id`;
   - `task_id`;
   - `document_key`;
   - `version_id`;
   - `status`;
   - `file_hash_sha256`;
   - `created_at`.
3. Убрать локальную имитацию preview через `setTimeout`.
4. Подключить `startPreview` и `waitPreview`.
5. Маппить статусы Gateway в UI-статусы:
   - `uploaded` -> "Загружен";
   - `previewing`/`processing` -> "Предпросмотр";
   - `completed`/`ready_for_approve` -> "Нужна проверка";
   - `approved` -> "Принят";
   - `discarded` -> "Отклонен";
   - `failed` -> "Ошибка".
6. Approve/reject делать через `draftsApi.decide`.
7. Delete делать через `draftsApi.delete`.
8. После approve инвалидировать query:

Критерий готовности: вкладка не теряет текущую UX-структуру, но решения и статусы идут через Gateway.

### Шаг 5. Сделать метаданные рабочими, но не навязчивыми

1. Оставить кнопку "Метаданные" и свернутый блок.
2. `source_type` оставить обязательным, но с дефолтом.
3. Остальные поля оставить опциональными.
4. Передавать заполненные поля в `draftsApi.create`.
5. После preview показывать извлеченные Gateway metadata в карточке черновика.
6. Если пользователь вводил metadata вручную, показывать различие:
   - "указано вручную";
   - "извлечено системой";
   - "требует проверки".

Критерий готовности: блок метаданных не перегружает экран, но реально влияет на upload.

### Шаг 6. Загрузка по ссылке

1. Оставить текущий UX: кнопка "Загрузить по ссылке" открывает модальное окно.

5. Отдельно зафиксировать вопрос backend: нужен ли серверный endpoint "загрузить документ по URL".

Критерий готовности: UI не обещает успешную загрузку по ссылке, если Gateway фактически ничего не получил.

Критерий готовности: база знаний работает как электронная библиотека, а не как смешанный экран обработки.

### Шаг 8. Подключить chat longpoll

Файл: `frontend/src/utils/http.ts`, компонент чата.

1. После `POST /chat/sessions/{id}/messages` сохранять `message_id`.
2. Ждать результат через `GET /chat/sessions/{id}/messages/{message_id}?longpoll=15`.
3. Если longpoll вернул промежуточный статус, повторить ожидание ограниченное число раз.
4. Если longpoll не дал результата, перейти в controlled error state.
5. Не запрашивать всю сессию как основной способ получения ответа.
6. Обработать статусы:
   - `pending` -> сообщение принято;
   - `enriching` -> обогащение запроса;
   - `searching` -> поиск источников;
   - `generating` -> генерация ответа;
   - `enriching_citations` -> подготовка цитат;
   - `answered` -> показать ответ;
   - `failed` -> показать ошибку.

Критерий готовности: чат следует рекомендованному Query Service flow.

Критерий готовности: навигация отражает реальные сценарии, а не технические сущности.

### Шаг 11. Администрирование, артефакты, журналы

1. Убрать карточки "Документы" и "OCR" из администрирования.

Критерий готовности: администрирование не дублирует обработку базы знаний и не показывает неподтвержденные mock-артефакты.

### Шаг 12. Проверка и приемка

После каждого крупного слоя:

1. `npm run lint`.
2. `npm run build`.
3. Smoke UI на `3300`.
4. Проверка Gateway mode без mock fallback.
5. Проверка demo mode отдельно.

Ручные сценарии:

1. Login без выбора роли.
2. Чат: отправить вопрос, дождаться ответа, открыть источник.
3. База знаний: открыть раздел, выбрать документ, открыть preview, развернуть, скачать.
4. Обработка базы знаний: выбрать файл, создать черновик, запустить preview, принять/отклонить.
5. Очередь обработки: увидеть реальные элементы или честный empty/error state.
6. Журнал обработки: увидеть реальные события или честный empty/error state.
7. Проверить роли: пользователь, администратор знаний, системный администратор.

## Что не делать сразу

- Не переписывать весь UI.
- Не менять дизайн-фреймворк.
- Не удалять компоненты поиска и администрирования до smoke-проверки.
- Не строить артефакты и pipeline-журналы на mock-данных в Gateway-режиме.
- Не использовать `/tasks/*` как пользовательский основной API: этот маршрут считается internal; внешний UI работает через `/drafts/*` и `/documents/*`.
- Не создавать "успешные" локальные черновики в Gateway-режиме, если Gateway не принял файл.

## Итоговая стратегия

Самый правильный первый практический шаг — начать с `http.ts` и `draftsApi`. Без этого любые правки вкладки "Обработка базы знаний" будут косметикой, а не закрытием API gap.

Дальше нужно переподключать уже существующую визуальную структуру к реальным Gateway-операциям. Это позволит сохранить текущий внешний вид, но убрать локальные имитации и получить интерфейс, который действительно работает по свежему backend-контракту.
