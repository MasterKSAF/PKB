# Мемо встречи: адаптация UI Final к новой документации Gateway

Дата: 19.06.2026

## Короткий вывод

UI Final нужно адаптировать к обновленной модели Gateway/Registry: разделить загрузку файлов, работу с черновиками, реестр документов и журнал обработки. Главный принцип: UI не должен имитировать готовые метаданные на этапе загрузки файла; метаданные, JSON, `title_key`, уведомления и статусы должны приходить из Gateway после обработки черновика.

## Что решили по интерфейсу

1. Вкладку "Обработка базы знаний" нужно разделить на четыре рабочие зоны: загрузка/очередь, черновики/метаданные, реестр документов, журнал обработки.
2. Кнопка "Создать черновики" должна только отправлять выбранные файлы в Gateway и создавать draft; заполнение метаданных начинается после обработки draft pipeline-ом.
3. Список черновиков должен быть компактным, с понятным статусом, индикаторами уведомлений и выбором активного черновика.
4. Главная рабочая область выбранного черновика должна начинаться со сверки и правки метаданных, ниже должны быть readonly-блоки Raw JSON, данные Gateway, классификация, уникальность, уведомления и история состояний.
5. Предпросмотр документа должен работать как в чате: открываться справа, разворачиваться на весь экран через иконку и не занимать основной сценарий работы с метаданными.
6. Принятые документы должны уходить из активных черновиков в реестр документов, где показываются карточка, версии, `title_key`, хэши, сроки действия и preview.

## Что нужно реализовать

1. Обновить UI-модели под новые поля Gateway/Registry: `title_key`, `title_hash_sha256`, `notifications`, `critical_count`, `has_notifications`, `valid_from`, `valid_until`, `document_id`, `version_id`, `raw_data`.
2. Переделать загрузку файлов: множественный выбор, список выбранных файлов, удаление файла до отправки, создание черновиков через Gateway.
3. Переделать работу с черновиком: получать полную карточку через `GET /drafts/{id}`, показывать метаданные из Gateway и сохранять ручные правки только через подтвержденный API.
4. Настроить доступность кнопок по статусам: approve/reject/delete/reprocess не должны быть активны, если Gateway не разрешает действие для текущего статуса.
5. Добавить отображение `title_key` как человекочитаемого объяснения бизнес-ключа, из которого считается `title_hash_sha256`.
6. Добавить блок уведомлений обработки, чтобы статусы `review_required`, warning/error/critical были понятны оператору.

## Стоперы для backend

1. В документации есть противоречие по `review_required`: в одном месте решение идет через `PATCH /drafts/{id}/decide`, в другом через `PATCH /drafts/{id}/operator-confirm`.
2. Не подтвержден публичный Gateway API для сохранения `metadata_overrides`; без него UI не может надежно сохранять ручные правки метаданных.
3. В документации расходятся названия замечаний: `notifications[]` и `issues[]`; для UI нужно одно публичное поле.
4. Статус `validation` есть в FSM, но не везде указан в enum статусов draft API.
5. Неясно, возвращаются ли `valid_from` и `valid_until` уже на стадии черновика или только в Registry после approve.
6. Enum `source_type` расходится по документам: в новых примерах есть `RMRS`, но в части таблиц он отсутствует.
7. Не подтвержден read-only контракт для журнала pipeline/task steps через Gateway.

## Рабочий порядок

Сначала нужно синхронизировать локальный `develop` с актуальным `origin/develop`, не потеряв текущие UI-правки. После этого безопаснее идти слоями: API-типы, загрузка файлов, список черновиков, рабочая область черновика, preview, approve/reject, реестр документов, журнал обработки. После каждого слоя нужны `lint`, `build` и smoke-тест на Gateway.
