# Guide — Архитектурные решения и ориентиры

## Тестирование Integration Service

### Два уровня тестов

1. **Локальные тесты** (`test_files.py`, `test_meridian.py`, `test_external.py`, `test_main.py`)
   - Используют `TestClient(app)` + SQLite in-memory + временные директории
   - Не требуют внешних зависимостей
   - Проверяют корректность API, обработку ошибок и граничные случаи

2. **Docker-зависимые тесты** (`live_server_check.py`)
   - Используют `httpx.Client()` для запросов к реальному серверу
   - Проверяют сквозную работу: файловый lifecycle, экспорт в Meridian, статус внешних систем
   - Целевой адрес задаётся через переменную окружения `LIVE_SERVER_URL`
   - По умолчанию: `http://localhost:8100`, в `recheck.bat` — `http://localhost:18085` (порт из Docker)

### Изоляция Docker-зависимых тестов

- Файл **переименован** в `live_server_check.py` — не подпадает под шаблон `test_*.py`, поэтому pytest не подхватывает его при обычном запуске
- Запускаются **только** через `service_checker/docker/recheck.bat` (секция 8), где Docker уже поднят
- Такой подход гарантирует, что обычный `pytest integration_service/tests/` не упадёт из-за отсутствия Docker

### Переключение между локальным и удалённым сервером

- `LIVE_SERVER_URL=http://195.70.195.203` — тесты идут на удалённый сервер
- Без переменной — тесты идут на `localhost:8100` (локально) или `localhost:18085` (через recheck.bat)
- Это позволяет прогонять одни и те же сценарии и на локальном экземпляре, и на staging/production

### Почему не TestClient для живых тестов

`TestClient` форсирует ASGI-запросы в рамках процесса и не может проверить реальную сетевую связность, HTTPS, прокси, DNS и т.д. Для сквозной проверки используется `httpx` с реальным HTTP-вызовом.
