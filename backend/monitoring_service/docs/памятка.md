## **Памятка по работе с логами, трейсами и метриками** 

## **(на основе рабочей конфигурации SigNoz \+ OpenTelemetry)**

\================================== ПО ЛОГАМ \==================================

### **1\. Уровни логов и их назначение**

| Уровень | Когда использовать | Пример оформления (код) |
| :---- | :---- | :---- |
| DEBUG | Диагностика, детали выполнения, входные параметры (но не секреты) | log.debug(f"Processing item {item\_id}, retry {retry}") |
| INFO | Успешные операции, изменения состояния, старт/стоп сервиса, генерация чисел | log.info(f"Generated number: {number}") |
| WARNING | Нештатные ситуации, которые не прерывают работу (повторные попытки, устаревшие параметры) | log.warning(f"Retry {n} for request {req\_id}") |
| ERROR | Исключения, ошибки внешних сервисов, валидационные ошибки (с указанием причины) | log.error(f"Service A returned {status\_code}: {text}") |
| EXCEPTION | Автоматически добавляет стектрейс; используйте внутри except вместо error | log.exception("Failed to call service B") |

Логика заложения:
* DEBUG – для разработчика при поиске проблем. Подробная отладка, только в dev-окружении.  
* INFO – для оператора, чтобы понимать бизнес-поток. Нормальный рабочий процесс.  
* WARNING – требует внимания, но не срочного вмешательства. Нештатная ситуация без остановки.  
* ERROR – сигнал для алерта, требует исправления. Ошибка в одном запросе.  
* EXCEPTION \- сервис не может работать.

Обязательные логические точки:
* Начало обработки запроса (если есть входящие данные): log.debug(...)  
* Успешное завершение операции: log.info(...)  
* Любое исключение (кроме тех, что пробрасываются фреймворку): log.error(..., exc\_info=True) или log.exception(...)  
* Обращение к внешнему сервису (успех или ошибка): log.info или log.error  
* Все данные внутри вызова, меняющие состояние системы, обязательно логируются.  
* Не делать Health-check эндпоинтов ни в  INFO нигде еще..  
* Логировать начало и успешное завершение каждой бизнес-операции.


### **2\. Оформление JSON-лога (фиксированные поля)** \!\! уже *настроено в библиотеке telemetry.py \!\!* 
```text
json  
{  
  "timestamp": "2026-06-12 10:00:00,123",
  "severity": "INFO",
  "name": "service-a",
  "message": "Check 2: yes",
  "pathname": "/app/main.py",
  "lineno": 42,
  "trace_id": "abc123...",   // добавляется автоматически
  "span_id": "def456..."      // добавляется автоматически 
}
```
Корреляция логов с трейсами (обязательные поля)  
Каждый лог внутри обработки HTTP-запроса или внутреннего вызова должен содержать:  
```text
json  
{  
  "trace_id": "0af7651916cd43dd8448eb211c80319c",
  "span_id": "b7ad6b7169203331"
}  
```
В проекте эти поля автоматически добавляются через LoggingHandler от OpenTelemetry. При проверке логов в SigNoz trace\_id должно быть не 00000000000000000000000000000000.  
Если trace\_id нулевой — проблема в инструментировании:

* Убедитесь, что декорирование FastAPI работает через instrument\_fastapi()  
* Проверьте, что HTTP-клиент в сервисе C обёрнут в HTTPXClientInstrumentor

### **3\. Чего НЕ делать при логировании:**

* Использовать print() вместо logging.  
* Логировать пароли, токены, персональные данные и другие секреты.  
* Вкладывать в extra объекты глубже одного уровня (например, extra={"user": {"id": 1}} — плохо, extra={"user\_id": 1} — хорошо).  
* Логировать Health-check эндпоинты на уровне INFO (только DEBUG или вообще без логов).  
* Вкладывать объекты в extra глубже одного уровня.  
* Использовать level=logging.WARNING как уровень по умолчанию.(в telemetry.py по умолчанию INFO)  
* Логировать каждый шаг тяжелого цикла(\>1000 запросов/с).  
* Логировать полные тела запросов/ответов без фильтрации \- это нарушит JSON-схему.  
* Логировать стектрейсы на каждый debug.  
* Использовать f-строки для сообщения об ошибке и терять stack trace:
*\# ПЛОХО* log.error(f"Error: {e}")  
*\# ХОРОШО* log.error("Error", exc\_info\=True)

\================================== ПО ТРЕЙСАМ \==================================

### **4\. Трейсы (автоматические \+ ручные)**

Автоматические – уже работают через instrument\_fastapi и HTTPXClientInstrumentor \- они автоматически собирают все входящие HTTP-запросы и исходящие вызовы через httpx. \!\! уже *настроено в библиотеке telemetry.py \!\!* 

**Шаги для ручного добавления спанов (редко нужно)**
| Шаг | Код | Куда вставить |
| :---- | :---- | :---- |
| 1 | from opentelemetry import trace | В начало файла |
| 2 | tracer \= trace.get\_tracer(service\_name) | После setup\_observability |
| 3 | with tracer.start\_as\_current\_span("span\_name") as span: | Обернуть блок кода |

### 

### 

### **Пример ручного трейса внутри эндпоинта**
```text
python  
from opentelemetry import trace   # ШАГ 1

# ... после setup_observability
tracer = trace.get_tracer(service_name)   # ШАГ 2

@app.post("/process")
async def process(data: dict):
    with tracer.start_as_current_span("process_data") as span:   # ШАГ 3
        span.set_attribute("input.value", data.get("value"))
        result = data.get("value") * 2
        log.info(f"Processed: {result}")
        return {"result": result}

```

**Что нельзя делать с трейсами:**
* Не отключайте автоматическое инструментирование HTTPX – оно нужно для распределённой трассировки.  
* Не используйте разные пропагаторы в разных сервисах.  
* Не передавайте большие объёмы данных в атрибутах спана (ограничение 512 байт на атрибут).

\================================== ПО МЕТРИКАМ \================================

### 

### **5\. Метрики (кастомные)**

Метрики настраиваются через meter\_provider, который возвращает setup\_observability.

### 

### 

### **Шаги для добавления кастомных метрик**

| Шаг | Действие | Пример кода |
| :---- | :---- | :---- |
| 1 | Получить meter из meter\_provider | meter \= meter\_provider.get\_meter(service\_name) |
| 2 | Создать счётчик (counter) или гистограмму | counter \= meter.create\_counter("name", description="...") |
| 3 | Инкрементировать счётчик в нужном месте | counter.add(1, {"attribute": "value"}) |

### 

### 

### **Пример кода с метриками (вставьте после вызова setup\_observability)**
```text
python  
# ==================== ШАГ 1: получаем meter ====================
meter = meter_provider.get_meter(service_name)


# ==================== ШАГ 2: создаём метрики ====================
requests_total = meter.create_counter(
    "my_requests_total",
    unit="1",
    description="Total number of requests"
)
error_total = meter.create_counter(
    "my_errors_total",
    description="Total errors"
)


# ==================== ШАГ 3: используем метрики в коде ====================
@app.post("/process")
async def process(data: dict):
    requests_total.add(1, {"endpoint": "/process"})   # инкремент
    try:
        # ... логика
        return {"ok": True}
    except Exception:
        error_total.add(1, {"error_type": "validation"})
        raise

```
**Что нельзя делать с метриками:**

* Не создавайте метрики внутри циклов с большим числом итераций (рекомендуется создавать один раз при старте).  
* Не используйте атрибуты с высокой кардинальностью (например, user\_id, request\_id) – это вызовет взрыв памяти в ClickHouse.  
* Не используйте динамические имена метрик – все имена должны быть фиксированы.
