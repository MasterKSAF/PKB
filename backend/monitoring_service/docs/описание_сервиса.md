### **Описание проекта системы мониторинга SigNoz** 

Подробнее про SigNoz на [https://github.com/SigNoz](https://github.com/SigNoz) 

**Описание**: Архитектура системы мониторинга с SigNoz построена вокруг единого стандарта OpenTelemetry (OTel), который обеспечивает vendor-нейтральный сбор и передачу данных. Центральным узлом выступает OpenTelemetry Collector, интегрированный в SigNoz. Он спроектирован для высокой масштабируемости и отказа от "склеивания" разнородных инструментов в пользу унифицированного решения. Конфигурация Collector (встроенного в SigNoz) предварительно настроена для записи в ClickHouse. ClickHouse выбран благодаря высокой производительности при работе с высокой кардинальностью данных и эффективному сжатию.

**Архитектура:** три FastAPI-сервиса (A, B, C) → OpenTelemetry SDK → OTLP (gRPC) → SigNoz-коллектор → ClickHouse → SigNoz UI. Все компоненты запущены в Docker, сеть signoz-net.

**Ключевой принцип:** все данные проходят через OpenTelemetry → единый коллектор → единое хранилище → единый интерфейс. Это обеспечивает корреляцию логов, трейсов и метрик без ручного связывания.


В проект приложена  структура папок с тестовыми сервисами А,Б,С, для примера и проверки.

**Тестовые сервисы А,Б,С.**  
Работа сервисов происходит следующим образом: 
- Сервис С каждые 5-15 секунд генерирует число от 1 до 10 (включительно) и передает сервису А его как входящее значение, а в ответ получает статус: да или нет.   
- Сервис А получает число от сервиса С и проверяет его четность, если число четное, то возвращает ответ статус да, если нечетное, то ответ статус нет, если число выходит за диапазон от 1 до 5 включительно то генерируется исключение и ничего не возвращает.   
- Если сервис С в ответе от сервиса А получает статус да, то он это число передает на вход сервиса Б, который возвращает букву алфавита из словаря(1:буква\_*а, 2:буква\_б;4:буква\_г,5:буква\_д*) по ключу входящего числа, цифра 3 вызывает исключеие и ничего не возвращает.   
- Все исключения и метрики и процессы внутри сервиса (что получил/отдал/как обработал) логируются, так же собираются трейсы(запуски и запросы/ответы между всеми сервисами).

**Компоненты и их функции**
| Компонент | Роль | Технология / порт |
| :---- | :---- | :---- |
| Сервис A | Проверка четности числа (1–5) | FastAPI, порт 8000 |
| Сервис B | Маппинг числа в букву (словарь) | FastAPI, порт 8001 |
| Сервис C | Генератор чисел (1–10), вызов A и B | FastAPI, порт 8002 |
| Telemetry lib | Единая настройка OTLP-экспорта, JSON-логов | setup\_observability() |
| SigNoz-коллектор | Приём OTLP, преобразование, маршрутизация | OpenTelemetry Collector, порт 4317 (gRPC) |
| ClickHouse | Хранение логов, трейсов, метрик | СУБД колоночная |
| SigNoz UI | Визуализация, дашборды, алертинг | Веб-интерфейс, порт 3301 |

### **Логика работы:**

### **1.Поток данных внутри сервисов**

#### 1.1 Логи

* Каждый сервис вызывает setup\_observability() → создаёт корневой логгер с двумя хендлерами:  
  * LoggingHandler (OTLP) – отправляет логи через gRPC на коллектор.  
  * StreamHandler с JsonFormatter – выводит JSON-логи в stdout.  
* Формат JSON: {"timestamp": "...", "severity": "INFO", "name": "service-a", "message": "...", "pathname": "...", "lineno": ...}  
* Логи обогащаются trace\_id и span\_id из активного спана (если есть).

#### 1.2 Трейсы

* Автоматическое инструментирование через FastAPIInstrumentor и HTTPXClientInstrumentor:  
  * Каждый входящий HTTP-запрос становится корневым спаном.  
  * Исходящие вызовы (httpx.AsyncClient) становятся дочерними спанами.  
* Пропагаторы (TraceContextTextMapPropagator \+ B3MultiFormat) передают контекст через HTTP-заголовки (traceparent, b3).  
* Трейсы экспортируются через OTLPSpanExporter на коллектор.

#### 1.3 Метрики

* Автоматические метрики HTTP (количество запросов, длительность, ошибки) – от instrumentation.  
* Кастомные метрики (например, generation\_tasks\_total, successful\_chains\_total, errors\_total в сервисе C) создаются через meter.create\_counter() и экспортируются через OTLPMetricExporter.

### **2\. Передача данных в SigNoz (вне сервисов)**

Протокол: OTLP/gRPC (порт 4317, insecure=true).  
Endpoint: signoz-otel-collector:4317 (имя контейнера в сети Docker).

* Сервисы отправляют все три типа телеметрии на один и тот же endpoint.  
* Переменные окружения в контейнерах:  
  * OTEL\_EXPORTER\_OTLP\_ENDPOINT  
  * OTEL\_EXPORTER\_OTLP\_INSECURE=true

Коллектор (SigNoz):

* Предварительно сконфигурирован на приём OTLP (ресивер otlp).  
* Преобразует и отправляет логи/трейсы/метрики в ClickHouse (экспортер clickhouse).

ClickHouse:

* Хранит логи в таблицах otel\_logs, трейсы в otel\_traces, метрики в otel\_metrics.  
* Сигнальная схема данных – стандартная для OpenTelemetry.

SigNoz UI:

* Запрашивает данные из ClickHouse через Query Service.  
* Отображает сервисы, трассировки, логи, метрики; позволяет строить дашборды и алерты.

### **Итог: как выглядит работа системы мониторинга**

1. Сервисы A, B, C запускаются в Docker, имеют переменные окружения для OTLP.  
2. При старте каждый сервис инициализирует OpenTelemetry (трейсы, метрики, JSON-логи).  
3. В процессе работы:  
   * Логи выводятся в stdout (JSON) и отправляются в коллектор.  
   * Трейсы автоматически собираются для каждого HTTP-запроса.  
   * Метрики обновляются (кастомные \+ HTTP).  
4. SigNoz-коллектор принимает OTLP/gRPC, сохраняет в ClickHouse.  
5. Инженер открывает SigNoz UI http://localhost:3301:  
   * Traces – видит цепочку C→A→B с длительностями.  
   * Logs – фильтрует по service.name, severity, trace\_id.  
   * Metrics – строит графики ошибок и успешных цепочек.

ВАЖНО\!  
В процессе настройки критически важно использовать фиксированные, проверенные версии зависимостей (как в финальной конфигурации), чтобы избежать проблем совместимости, которые возникали при попытках обновления библиотек. Все данные передаются синхронно по OTLP, что гарантирует целостность наблюдений.
