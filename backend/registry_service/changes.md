## 1. Несоответствия в API-эндпоинтах и логике обработки

### 1.1. Загрузка документов из Пайплайна 1 (`POST /registry/documents/`)
* **Требование спецификации (§3.3):** Эндпоинт должен принимать сложный обогащенный JSON (структура `validated_v3` / `for_rag_v1`), содержащий метаданные, разделы документа (`content[]`), терминологию (`terminology[]`) и ссылки (`references[]`). Сервис должен автоматически сегментировать документ, сохранять разделы в таблицу `registry.document_sections`, ссылки в `registry.document_references` и возвращать плоский массив разделов с проставленными ID.
* **Текущая реализация:** Принимает только плоский словарь с метаданными документа, создавая запись исключительно в таблице `documents`. Сегментация на разделы (`DocumentSection`), добавление терминов и перекрестных ссылок (`DocumentReference`) полностью отсутствуют.
* **Формат ответа:** Вместо специфицированной структуры ответа (`document_id`, `version_id`, `sections[]`, `registry`) эндпоинт возвращает полную сериализованную модель `DocumentSchema`.

### 1.2. Автоматический расчет `title_hash_sha256`
* **Требование спецификации (§3.3, §3.4):** Хеш бизнес-ключа `title_hash_sha256` должен вычисляться автоматически при создании документа по формуле: `SHA-256(era|source_type|mks_oks_code|okstu_code|doc_code|normalized_title)`. При обновлении любого из этих полей через `PUT / PATCH` хеш должен пересчитываться автоматически.
* **Текущая реализация:** Автоматический расчет и перерасчет хеша в методах CRUD (`create_document`, `update_document` в `api/v1/crud/document.py`) отсутствует. Поле заполняется только в том случае, если готовый хеш был передан извне в теле запроса.

### 1.3. Валидация и формат ответа при смене статуса (`PATCH /registry/documents/{document_id}/status`)
* **Требование спецификации (§3.6):** Эндпоинт принимает новый статус и возвращает аудит-структуру (`id`, `status`, `previous_status`, `history_id`, `updated_at`). Допустимые статусы строго ограничены списком FSM.
* **Текущая реализация:** Валидация статуса на соответствие списку FSM не выполняется. Эндпоинт возвращает полное тело обновленного документа `DocumentSchema`, а не специализированную аудит-структуру.

## 2. Расхождения в схемах базы данных (Модели SQLAlchemy)

### 2.1. Таблица и модель `format_registry` (§5.5)
* **Требование спецификации:** Должна существовать таблица реестра поддерживаемых форматов файлов и движков парсинга со структурой: `id`, `format_code` (unique), `mime_type`, `parser_engine`, `supported`, `created_at`.
* **Текущая реализация:** Модель `FormatRegistry` полностью отсутствует в коде (нет в папке `api/v1/models/`), эндпоинты для работы с ней не реализованы.

### 2.2. Составной первичный ключ в `Classifier` (§5.1)
* **Требование спецификации:** Таблица `classifier_node` должна использовать составной первичный ключ `(classifier_system, code)`.
* **Текущая реализация:** Используется суррогатный первичный ключ `id = Column(UUID)`. Поля `classifier_system` и `code` являются обычными колонками. Также в модели отсутствуют поля `effective_date` и `replaced_by`.

### 2.3. Недостающие поля в модели `Terminology` (§5.3)
* **Требование спецификации:** Запись терминологии должна содержать поля `is_case_sensitive` (boolean), `synonyms` (jsonb), `related_docs` (jsonb) и `scope` (jsonb).
* **Текущая реализация:** Данные поля в модели `Terminology` отсутствуют.

### 2.4. Недостающие поля в модели `Document` (§5.4)
* **Требование спецификации:** Таблица должна содержать поля `classifier_code` (nullable), `industry_code` (nullable) и `enterprise_id` (nullable).
* **Текущая реализация:** Указанные поля отсутствуют в SQLAlchemy модели `Document`.

## 3. Заглушки (Stubs) в коде эндпоинтов

Следующие эндпоинты в `api/v1/routes.py` содержат только временные заглушки без реальной бизнес-логики:
1. `POST /registry/classifiers/import` — возвращает статический JSON `{ "data": { "message": "File for Import accepted - not implemented yet" } }`.
2. `POST /registry/terminology/import` — возвращает статический JSON `{ "data": { "message": "Import accepted" } }`.
3. `POST /registry/documents/import` — возвращает статический JSON `{ "data": { "message": "Import accepted" } }`.
