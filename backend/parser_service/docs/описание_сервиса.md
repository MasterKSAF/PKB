
## **Сервис парсинга v1: архитектура, документация**

### **1\. Файловая архитектура и функции**

Ниже приведена структура проекта с описанием назначения каждого файла и основных функций.

app/

│   │   │   ├── result.py        # GET /parser/process/{id}/result – получение JSON результата
│   │   │   └── processes.py     # GET /parser/processes – список активных задач
│   │   ├── schemas.py           # Pydantic-модели запросов/ответов для v1

│   ├── normalizer.py            # Normalizer: оборачивает сырой JSON в контейнер (document_info, content, metadata)
│   ├── standardizer.py          # JsonStandardizer: преобразует JSON в целевой формат (document.source, block, quality)
│   └── pipeline/                # Пайплайн обработки
│       ├── context.py           # ProcessingContext – сквозной контейнер данных между шагами
│       ├── steps.py             # Шаги: Download, Validate, PagesTotal, Parse, UploadImages, Normalize, Standardize, SaveJsonToFile, StoreResult, TruncatePdf
│       └── pipeline.py          # Оркестратор – последовательное выполнение шагов

### **3\. Логика работы файлов и взаимодействия**


1. Запрос на обработку  
   * `process.py` (v1/v2) получает `ProcessRequest`.  
   * Для `full` режима: создаётся `TaskInfo`, сохраняется в `TaskStateStorage.add()`. Фоном запускается `_run_pipeline` → `Pipeline.create(mode="full")` → `Pipeline.run()`.  
   * Для `preview` (v2): вызывается `_sync_preview()` → `Pipeline.create(mode="preview")` – синхронно, ответ возвращается сразу.  
2. Пайплайн (pipeline.py)  
   * Инициализируется список шагов в зависимости от режима.  
   * Каждый шаг наследует `PipelineStep`, реализует `execute(ctx)`.  
   * `Pipeline.run()` итерирует шаги, передаёт контекст, обновляет прогресс (если `track_progress=True`).  
   * При ошибке – помечает задачу как `FAILED` и пробрасывает исключение.  
3. Шаги (steps.py)  
   * DownloadStep – скачивает файл из MinIO в `ctx.file_bytes`, сохраняет имя файла.  
   * ValidateStep – вызывает `Validator.validate()` (размер, MIME, безопасность).  
   * PagesTotalStep – определяет количество страниц через `PdfReader`.  
   * TruncatePdfStep (только preview) – обрезает PDF до `max_pages`.  
   * ParseStep – через `ParserFactory` получает парсер (PDF) и вызывает `parse()`, возвращает `ParseResult` (JSON и список изображений).  
   * UploadImagesStep (только full) – загружает изображения в MinIO, заменяет ссылки в JSON (`_temp_path` → `image_key`).  
   * NormalizeStep – оборачивает сырой JSON в контейнер `{"document_info": ..., "content": ..., "metadata": ...}`.  
   * StandardizeStep – преобразует контейнер в целевой формат через `JsonStandardizer.transform()`.  
   * SaveJsonToFileStep – опционально сохраняет JSON на диск (отладка).  
   * StoreResultStep – сохраняет финальный результат в `TaskStore.update_task()` со статусом `COMPLETED`.  
4. Парсер PDF (pdf\_parser.py)  
   * Сохраняет входные байты во временный PDF-файл.  
   * В отдельном потоке (`ThreadPoolExecutor`) вызывает `opendataloader_pdf.convert()`.  
   * Собирает все пути к изображениям из сгенерированного JSON, добавляет `_temp_path`.  
   * Возвращает `ParseResult` с JSON, списком изображений и `temp_dir`.  
5. Хранилище задач (task\_state\_storage.py)  
   * `TaskStateStorage` – `dict[int, TaskInfo]`.  
   * `update_task()` – обновляет атрибуты, увеличивает версию, уведомляет `TaskEventNotifier`.  
   * `wait_for_change()` – использует `TaskEventNotifier` для ожидания изменения версии (longpoll).  
   * Фоновая очистка – раз в час удаляет завершённые задачи старше TTL.  
6. Обработка ошибок  
   * Кастомные исключения (`FileNotFoundError`, `StorageError` и т.д.) наследуют `ParserServiceError`.  
   * В `exception_handlers.py` они перехватываются и возвращают JSON с полем `{"error": {...}}`.  
   * `RequestValidationError` преобразуется в `422 VALIDATION_ERROR`.  
   * Любые другие исключения – в `500 INTERNAL_SERVER_ERROR`.  
7. Логирование  
   * `setup_logging()` настраивает корневой логгер на вывод JSON в stdout.  
   * Все модули используют `logging.getLogger(__name__)`.  
   * Уровень управляется переменной окружения `LOG_LEVEL`.



### **4\. Подробная документация сервиса**

Parser Service – внутренний микросервис для извлечения текста, таблиц и изображений из PDF (с поддержкой DOC/DOCX в виде заглушек).  
Вход: ссылка на файл в MinIO (`file_key`).  
Выход: JSON‑контейнер со структурированным содержимым.  
Особенности: не имеет доступа к БД, состояние задач хранится в памяти (TTL 7 дней), longpoll на 15 секунд.

#### Эндпоинты

| Метод | URL (v1) | URL (v2) | Описание |
| :---- | :---- | :---- | :---- |
| POST | `/api/v1/parser/process` | `/api/v2/parser/process` | Асинхронная полная обработка (full) или синхронный предпросмотр (preview, только v2). Возвращает `task_id` и `status: accepted` (full) или документ (preview). |
| POST | `/api/v1/parser/preview` | – (встроен в v2) | Синхронный предпросмотр (первые `max_pages` страниц) для v1. |
| GET | `/api/v1/parser/process/{task_id}/status` | `/api/v2/parser/process/{task_id}/status` | Longpoll (таймаут 15 с) – возвращает статус, прогресс, кол-во страниц и т.д. |
| GET | `/api/v1/parser/process/{task_id}/result` | `/api/v2/parser/process/{task_id}/result` | Возвращает финальный JSON-контейнер (после завершения задачи). Для v2 обёрнут в `ResultResponse`. |
| GET | `/api/v1/parser/processes` | `/api/v2/parser/processes` | Список активных задач (статусы `accepted` или `processing`). |


#### Коды ошибок (в поле `error.code`)

| Код | HTTP статус | Описание |
| :---- | :---- | :---- |
| `FILE_NOT_FOUND` | 404 | Файл не найден в MinIO. |
| `FILE_TOO_LARGE` | 413 | Превышен максимальный размер файла (500 МБ). |
| `UNSUPPORTED_FORMAT` | 415 | MIME-тип не поддерживается (разрешён только `application/pdf`). |
| `PARSER_FAILED` | 500 | Критическая ошибка при парсинге (внутреннее исключение, таймаут, отсутствие JSON). |
| `STORAGE_ERROR` | 502 | Ошибка доступа к MinIO (сетевые проблемы, таймаут, неудачное создание бакета). |
| `TASK_NOT_FOUND` | 404 | Задача с указанным `task_id` не найдена в хранилище (или уже удалена). |
| `TASK_EXPIRED` | 410 | Результат задачи удалён по истечении TTL (7 дней). |
| `VALIDATION_ERROR` | 422 | Ошибка валидации входных данных (например, пустой `version_id`, недопустимые `options` в preview). |
| `INTERNAL_SERVER_ERROR` | 500 | Необработанное исключение (generic fallback). |
| `CANCELLED` | 500 | Задача отменена при graceful shutdown (возвращается через `update_task`). |
| `PIPELINE_TIMEOUT` | 500 | Превышен общий таймаут пайплайна (`pipeline_timeout`). |
| `EMPTY_RESULT` | 500 | Задача завершена, но результат отсутствует (пустой `task_info.result`). |
| `TASK_NOT_COMPLETED` | 409 | Попытка получить результат до завершения задачи. |

*Примечание:* `CANCELLED`, `PIPELINE_TIMEOUT`, `EMPTY_RESULT`, `TASK_NOT_COMPLETED` не описаны в `exceptions.py`, но могут возвращаться через `update_task` или `JSONResponse` в эндпоинтах.
