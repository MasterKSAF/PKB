## 🔴 КРИТИЧЕСКОЕ: добавить триггер `tsvector_update_trigger` в `db_diagrams.md`

В ER-диаграмме **полностью отсутствует**. В коде:

```sql
CREATE TRIGGER trg_chunks_tsv_update
    BEFORE INSERT OR UPDATE ON rag.document_chunks
    FOR EACH ROW
    EXECUTE FUNCTION tsvector_update_trigger(tsv, 'pg_catalog.russian', content);
```

**Комментарий:** без триггера поле `tsv` всегда NULL, и sparse search вернёт 0 результатов. Это **единственное несоответствие**, которое ломает функциональность.

## 🟡 Некритическое: `docs/database/db_diagrams.md`

### 1a. `VECTOR(1536)` → `VECTOR(1024)`

| Где | Что написано | Что должно быть |
|---|---|---|
| Таблица `rag.document_chunks`, поле `embedding` | `VECTOR(1536)` | `VECTOR(1024)` |
| Раздел «Ключевые условия и ограничения», п.6 | `VECTOR(1536)` | `VECTOR(1024)` |

**Комментарий:** размерность `embedding VECTOR(N)` в БД **обязана** совпадать с размерностью выходного вектора модели эмбеддингов. Сейчас: модель Qwen3-Embedding-0.6B выдаёт 1024 → в БД `VECTOR(1024)`. При смене на `Qwen3-Embedding-8B` (тоже 1024) DDL менять не нужно. А вот при переходе на другую модель с другой размерностью (например, 1536) — требуется изменить и DDL. При несовпадении dense search упадёт (`expected N dimensions, not M`). Sparse (`tsv`) — это tsvector для полнотекстового поиска, к размерности эмбеддингов отношения не имеет.

### 1b. `IVFFlat` → `HNSW`

| Где | Что написано | Что должно быть |
|---|---|---|
| Раздел «Ключевые условия и ограничения», п.6 | `IVFFlat` индекс для `cosine_similarity` | `HNSW` индекс для `cosine_similarity` |

**Комментарий:** в коде используется `USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`. HNSW быстрее, точнее, не требует периодического `reindex`.

### 1c. Добавить в `rag.document_chunks` поля

Поля есть в SQL (`init_schemas.sql`), но **отсутствуют в ER-диаграмме**:

| Поле | Тип в SQL | Описание |
|---|---|---|
| `chunk_strategy` | `TEXT` | В ER-диаграмме названо `strategy` — нейминг расходится |
| `tenant_id` | `TEXT NOT NULL DEFAULT 'default'` | Полностью отсутствует в ER-диаграмме |
| `bbox` | `JSONB` | Полностью отсутствует в ER-диаграмме для `document_chunks` |

**Комментарий:** код не читает эти поля — на поиск не влияют. Но ER-диаграмма должна отражать реальную схему.

### 1d. Добавить индексы

В ER-диаграмме перечислены не все индексы. Фактически создаются:

| Индекс | Тип | Таблица | Влияние на поиск |
|---|---|---|---|
| `idx_chunks_document` | B-tree | `rag.document_chunks(document_id)` | ⚡ **Только скорость** — JOIN по `document_id` без фильтра, ускоряет при большом количестве документов |
| `idx_chunks_section` | B-tree | `rag.document_chunks(section_id)` | ⚡ **Только скорость** — LEFT JOIN с секциями |
| `idx_chunks_tsv` | GIN | `rag.document_chunks(tsv)` | ⚡ **Только скорость** — без него `@@` сделает seq scan |
| `idx_chunks_embedding` | HNSW | `rag.document_chunks(embedding)` | ⚡ **Только скорость** — без него `<=>` сделает seq scan |

Все индексы влияют **только на скорость**, не на корректность.

## 🟡 Некритическое: `docker-compose` / Инфраструктура — обязательные расширения PostgreSQL

Перед запуском сервиса в БД должны быть установлены расширения. Без них поиск не работает:

| Расширение | Назначение | Без него |
|---|---|---|
| `vector` | Тип `VECTOR(N)` и оператор `<=>` (cosine distance) | Dense-поиск упадёт — тип данных не существует |
| `ltree` | Тип `LTREE` в `registry.document_sections` | Не создадутся таблицы `registry` |
| `pg_trgm` | Расширение для триграммного поиска | Упомянуто в ТЗ, но в коде пока не используется. Расширение создаётся в SQL, но не влияет на текущий поиск |

**Комментарий:** расширения создаются в `init_schemas.sql`. При развёртывании через голый SQL (без `create_all()`) это нужно делать явно: `CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS ltree; CREATE EXTENSION IF NOT EXISTS pg_trgm;`. Документация должна гарантировать, что deployer об этом знает.

### 5a. RAG Builder должен использовать тот же Infinity для согласованности моделей

RAG Builder (сервис, который режет документы на чанки и создаёт эмбеддинги) **обязан** использовать:
- Тот же экземпляр Infinity (тот же `EMBEDDING_BASE_URL`)
- Ту же модель (`EMBEDDING_MODEL`)
- Ту же размерность (`EMBEDDING_DIM`)

**Причина:** если RAG Builder создаёт эмбеддинги моделью A (размерность 1536), а RAG Search ищет моделью B (размерность 1024), то векторы в БД будут несовместимы — dense search либо упадёт (размерность), либо найдёт семантически нерелевантные результаты (разные модели). Infinity один — модель одна — размерность одна.

**Комментарий:** в документации PKB это нигде не зафиксировано. Рекомендуется добавить в `pipeline3-search.md` примечание о согласованности пайплайна чанкер → эмбеддер → поиск.
