# Спецификация конвертера-валидатора (Converter-validator)

> **Версия**: 1.0 (18.06.2026)
> **Сервис**: `converter-validator:8086`
> **Пайплайн**: 1 (Формирование документа), этап 1.5
> **Источники**: `converter_validator_service_api.md`, `pipeline1-formation_detail.md §3.2`, `normalizer_specification.md`, обсуждения 08.06, 16.06.

---

## 1. Назначение

Converter-validator — центральный сервис интеллектуальной обработки в Пайплайне 1. Он получает сырой JSON от OCR (для сканов) или Parser (для цифровых документов) и преобразует его в **иерархический, типизированный JSON** (`validated_v3`), пригодный для сохранения в Registry и последующей индексации RAG Builder.

**Сервис не имеет доступа к БД** (см. `converter_validator_service_api.md` §Сводная информация). Все данные для работы получает через тело запроса от Orchestrator.

### 2.2. Шаги обработки

| Шаг | Действие | Вход | Выход | Зависимости |
|-----|----------|------|-------|-------------|
| 1 | **Построение иерархии** — плоские блоки `raw_ocr_v4` преобразуются в структуру разделов, подразделов, абзацев, списков, таблиц, изображений, формул | `raw_ocr_v4.content[]` (плоский массив блоков) | Иерархическая структура с `clause`, `level`, `parent_clause`, `path` | Нет |
| 2 | **LLM-обработка** (если `use_llm = true`) — уточнение иерархии, классификация типов секций, нормализация сложных структур | Иерархия (шаг 1) | Уточнённая иерархия | Шаг 1 |
| 3 | **Извлечение метаданных** — `doc_code`, `title`, `document_type`, `year`, `revision`, `era`, `issuing_body`, `mks_oks_code`, `okstu_code`, `udk_code`, `adoption`, `replaces`, `amendments` | Иерархия (шаги 1–2) | `document.metadata` | Шаги 1–2 |
| 4 | **Валидация структуры** — проверка полноты данных, соответствия целевой схеме (`validated_v3`) | Иерархия (шаг 1) | `validation.structure_valid: bool` | Шаг 1 |
| 5 | **Классификация** — определение `era` (USSR/CIS/RF/CURRENT), `source_type` (gost/gost_r/ost/rd/tu/iso/dnv/astm), `jurisdiction`, `validity_status` | `document.metadata` (шаг 3) | `classification` с кодами МКС/ОКС, ОКСТУ, УДК | Шаг 3 |
| 6 | **Вычисление хэшей** — `file_hash_sha256` (SHA-256 от бинарного содержимого файла) и `title_hash_sha256` (бизнес-ключ по формуле нормализатора) | `file_hash_sha256`: файл; `title_hash_sha256`: метаданные (шаг 3) | `validation.fingerprint` | Шаг 3 |
| 7 | **Сопоставление** — поиск `predecessor_doc_id` / `successor_doc_id` по `title_hash_sha256` (через Registry). Если найден дубликат — `decision = manual` | `title_hash_sha256` (шаг 6) | `validation.matching` | Шаг 6 |
| 8 | **Валидация классификационных кодов** — проверка `mks_oks_code`, `okstu_code`, `udk_code` по справочнику Registry | Коды (шаг 5) | `classification_status`: `CONFIRMED`, `PENDING_REVIEW`, `NOT_FOUND`, `NOT_USED`, `UNASSIGNED` | Шаг 5, Registry |
| 9 | **Построение кросс-ссылок** — извлечение из текста ссылок на другие документы, нормализация `target_doc_code`, формирование `document.references[]` | Иерархия (шаги 1–2) | `document.references[]` | Шаги 1, 7 |

### 2.3. Режимы работы

| Режим | Эндпоинт | Шаги | LLM | Запись в БД |
|-------|----------|------|-----|-------------|
| **Preview** | `POST /converter/preview/metadata` | Только шаг 3 (извлечение базовых метаданных: `doc_code`, `title`, `document_type`, `year`, `revision`) | Нет (или быстрый вызов с ограничением) | Нет |
| **Full** | `POST /converter/convert` | Шаги 1–9 (полный цикл) | Да (управляется `use_llm`) | Нет |
| **Standalone validate** | `POST /validate/document` | Шаги 4–8 (только валидация, без переконвертации) | Нет | Нет |

## 3. Сценарии использования

### Сценарий А: Нормальный поток — цифровой PDF

**Контекст:** Загружен цифровой PDF «ГОСТ 2.105-95 ЕСКД» (не скан, текстовый слой есть).

**Поток:**

1. **Вход:** Parser возвращает `raw_ocr_v4` с полным content (все страницы, таблицы, изображения, метаданные).
2. **Шаг 1 (иерархия):** Плоские блоки Parser преобразуются в иерархию:
   - `ЕСКД` → `title`, `heading_level=1`
   - `1 Область применения` → `clause="1"`, `level=1`
   - `2 Нормативные ссылки` → `clause="2"`, `level=1`
   - `2.1` → `clause="2.1"`, `level=2`, `parent_clause="2"`
   - Таблицы с атрибутами `colspan`/`rowspan` объединяются в единую структуру.
3. **Шаг 2 (LLM):** LLM уточняет границы разделов, исправляет ошибки иерархии (например, заголовок без `heading_level`).
4. **Шаг 3 (метаданные):** Извлечено:
   - `doc_code`: `2.105-95`
   - `title`: `"Единая система конструкторской документации"`
   - `document_type`: `normative`
   - `era`: `RF` (год ≥ 2000)
   - `source_type`: `gost_r`
5. **Шаг 6 (хэши):** Вычислен `title_hash_sha256`.
6. **Шаг 7 (сопоставление):** По `title_hash_sha256` в Registry не найдено совпадений → `decision = auto`.
7. **Выход:** `validated_v3` с `status: completed`.

**Результат:** Иерархический JSON готов для передачи в Registry.

---

### Сценарий Б: Скан-документ с ошибками OCR

**Контекст:** Загружен сканированный PDF «ГОСТ 20868-81 Стойки...». Качество скана среднее, OCR допустил ошибки.

**Поток:**

1. **Вход:** OCR возвращает `raw_ocr_v4`:
   - Часть блоков имеет низкую `confidence` (< 0.7)
   - Некоторые заголовки не распознаны (плоские блоки без `heading_level`)
   - Есть разрывы таблиц на смежных страницах
2. **Шаг 1 (иерархия):** Блоки с низкой `confidence` помечаются `needs_review`.
   - Таблицы с перекрывающимися bbox объединяются.
3. **Шаг 2 (LLM):** LLM обрабатывает блоки с `needs_review`:
   - Восстанавливает заголовки
   - Исправляет OCR-ошибки в терминах (сверка с терминологическим реестром)
4. **Шаг 3 (метаданные):**
   - `doc_code`: `20868-81`
   - `era`: `USSR` (год 1981)
   - `mks_oks_code`: `47.020` (найден на первой странице)
   - `source_type`: `gost`
5. **Шаг 8 (валидация кодов):** `mks_oks_code = 47.020` найден в справочнике Registry → `mks_status: CONFIRMED`.
6. **Выход:** `validated_v3` с `validation.structure_valid: true`, `llm_usage` заполнен.

**Результат:** Документ успешно конвертирован, OCR-ошибки исправлены LLM.

---

### Сценарий В: Документ без метаданных (ручное заполнение)

**Контекст:** Администратор вносит документ через `POST /registry/documents` без файла (Сценарий Б из `purgatory_scenario.md`). Converter-validator не участвует.

> **Важно:** Converter-validator работает только с сырым JSON от OCR/Parser. Если метаданные вводятся вручную через Registry, конвертер не вызывается.

---

### Сценарий Г: Ошибка LLM — таймаут

**Контекст:** Документ большого объёма (200+ страниц), LLM-обработка превышает таймаут.

**Поток:**

1. **Запрос:** `POST /converter/convert` с `use_llm: true`, `llm_timeout: 60`.
2. **Шаги 1–3:** Выполнены успешно.
3. **Шаг 2 (LLM):** LLM-запрос не укладывается в 60 секунд.
4. **Ошибка:** Converter-validator возвращает `502 LLM_TIMEOUT`.
5. **Оркестратор:** При повторной попытке увеличивает `llm_timeout` (до 120 с) или отключает LLM (`use_llm: false`) для данного документа.
6. **Fallback:** При `use_llm: false` конвертация выполняется без LLM — иерархия строится эвристически, что может снизить качество.

**Результат:** Документ обработан без LLM. В `llm_usage` указан `processing_time_ms` с exceeded-меткой.

---

### Сценарий Д: Пустой вход (0 страниц)

**Контекст:** OCR/Parser вернул пустой JSON (0 страниц).

**Поток:**

1. **Вход:** `raw_ocr_v4` с `document.source.page_count = 0`.
2. **Шаг 3 (метаданные):** Невозможно извлечь `doc_code` и `title`.
3. **Ошибка:** `422 METADATA_EXTRACTION_FAILED`.
4. **Оркестратор:** Переводит черновик в `discarded` с кодом `EMPTY_DOCUMENT`.

**Результат:** Черновик отклонён, документ не создан.

---

### Сценарий Е: Документ с латинскими аватарами в названии

**Контекст:** Загружен PDF, где в названии «ГОСТ Р 2.105-95 ЕКСД» буква `C` — латинская (вместо кириллической `С`). См. `normalizer_specification.md` §3.3.

**Поток:**

1. **Шаг 3 (метаданные):** Извлечено `title: "ГОСТ Р 2.105-95 ЕКСД"` с латинским аватаром.
2. **Шаг 2 (LLM):** LLM обнаруживает смешанный скрипт → исправляет на `"ЕКСД"`.
3. **Шаг 5 (нормализация):** Нормализатор (см. `normalizer_specification.md`):
   - Детект аватара: латинская `C` → кириллическая `с`
   - `needs_review = true`
4. **Шаг 7 (сопоставление):** По `title_hash_sha256` найдена существующая карточка ГОСТ Р 2.105-95.
5. **Решение:** `decision = manual` (обнаружен аватар → требуется подтверждение).
6. **Оркестратор:** Запрашивает подтверждение у пользователя.

**Результат:** Черновик ожидает решения пользователя. При подтверждении — привязка как новая версия к существующей карточке.

---

### Сценарий Ж: Документ с недействительным кодом МКС/ОКС

**Контекст:** На первой странице указан код `МКС 99.999`, которого нет в справочнике.

**Поток:**

1. **Шаг 3 (метаданные):** Извлечён `mks_oks_code: "99.999"`.
2. **Шаг 8 (валидация):** Запрос к Registry — код не найден в `registry.classifier_registry`.
3. **Результат:** `mks_status: PENDING_REVIEW`.
4. **Выход:** `decision: manual`.
5. **Оркестратор:** Показывает предупреждение: «Код МКС 99.999 не найден в справочнике. Укажите правильный код или подтвердите».

**Результат:** Документ ожидает ручного подтверждения кода.

## 4. Маппинг типов блоков

Converter-validator преобразует плоские блоки из схемы `raw_ocr_v4` в типизированные секции схемы `validated_v3`.

| `block[].type` (OCR/Parser) | `section.type` (validated_v3) | Примечание |
|-----------------------------|-------------------------------|------------|
| `headerFooter` | `headerFooter` | Прямое соответствие |
| `heading` | `text` | Добавляется `heading_level` |
| `paragraph` | `text` | Стандартный текстовый блок |
| `text_block` | `textBlock` | Включает вложенные `block[]` с font-разметкой |
| `list` | `list` | Конвертируется в `content.items[]` с `numbering_style` |
| `table` | `table` | Объединяет разорванные таблицы (по координатам, заголовкам) |
| `image` | `image` | Сохраняется `image_key` / `file_key` |
| `caption` | Вливается в parent | Принадлежит таблице, рисунку или формуле (отдельная секция не создаётся) |
| `formula` | `formula` | Сохраняется `latex` + `meaning` |
| `drawing` | `image` | Тип `drawing` объединён с `image` (D56, API-B1) |

## 5. Использование LLM

### 5.1. Когда LLM включается

LLM используется в шаге 2 полного цикла (`POST /converter/convert`). Управляется параметром `use_llm`.

**LLM применяется для:**

| Задача | Описание | Без LLM (fallback) |
|--------|----------|-------------------|
| Построение иерархии | Уточнение границ разделов, восстановление заголовков | Эвристики по `heading_level`, `font_size`, `bbox` |
| Классификация типов секций | Определение типа секции по контексту | По `block[].type` напрямую |
| Извлечение метаданных | `doc_code`, `title`, `era`, классификационные коды | Регулярные выражения (см. `normalizer_specification.md` §4) |
| Нормализация названия | Исправление латинских аватаров, римских цифр | Токенизация + terminology_registry |
| Построение кросс-ссылок | Извлечение `target_doc_code` из контекста | Регулярные выражения |

### 5.2. Модель LLM по умолчанию

| Параметр | Значение по умолчанию | Источник |
|----------|----------------------|----------|
| Модель | `deepseek 4 flash` (внешнее API) | P13-5, `app_settings.llm.api_url` |
| `temperature` | `0.2` | P13-5 |
| `max_tokens` | `1024` | P13-5 (для preview); `4096` (для full) |
| `top_p` | `0.95` | P13-5 |
| `system_prompt` | из каталога `prompts/` | P13-5 |

### 5.3. Таймауты и повторные попытки

| Ситуация | Действие | Код ошибки |
|----------|----------|------------|
| LLM-запрос превысил `llm_timeout` | Прерывание, возврат ошибки | `502 LLM_TIMEOUT` |
| LLM-сервис недоступен | Повторная попытка (3 retry, exponential backoff) | `502 LLM_TIMEOUT` |
| LLM вернул пустой ответ | Fallback на эвристики | `validation.structure_valid = false` |

## 6. Нормализация и бизнес-ключ

### 6.1. Бизнес-ключ `title_hash_sha256`

Вычисляется нормализатором (см. `normalizer_specification.md` §2.1):

```
title_hash_sha256 = SHA-256(era | source_type | mks_oks_code | okstu_code | doc_code | normalized_title)
```

**Converter-validator** вычисляет `title_hash_sha256` на шаге 6 и передаёт в `validation.fingerprint`. **Оркестратор** использует этот хэш для проверки уникальности через `POST /registry/documents/check-uniqueness`.

### 6.2. Нормализация `doc_code` для кросс-ссылок

Алгоритм (см. `normalizer_specification.md` §8):

1. **Извлечение** — из текста удаляются префиксы (`ГОСТ`, `ГОСТ Р`, `ISO`, `DNV`, etc.) и суффиксы (год, название).
2. **Очистка** — удаление незначащих символов (пробелы, табуляции, точки в конце, скобки).
3. **Форматирование** — `doc_code` приводится к нижнему регистру, дефисы и слеши сохраняются.
4. **Поиск** — по нормализованному `doc_code` резолвер Registry ищет совпадение.

### 6.3. Извлечение кодов классификации

Алгоритм (см. `normalizer_specification.md` §4):

| Код | Паттерн | Статус при успехе | Статус при неудаче |
|-----|---------|-------------------|-------------------|
| МКС/ОКС | `(?:МКС\|ОКС\|ICS)\s*[:\s]*?(\d{2}(?:\.\d{3}(?:\.\d{2})?)?(?:-\d{2})?)` | `CONFIRMED` | `NOT_FOUND` или `PENDING_REVIEW` |
| ОКСТУ | `(?:ОКСТУ\|ОК\.СТУ)\s*[:\s]*?(\d{2}(?:\.\d{2}){1,2})` | `CONFIRMED` | `NOT_USED` (для иностранных) или `NOT_FOUND` |
| УДК | `(?:УДК\|UDC)\s*[:\s]*?([\d.:]+)` | `CONFIRMED` | `NOT_FOUND` |

## 7. Ключевые принципы

| Принцип | Описание | Сценарии | Источник |
|---------|----------|----------|----------|
| **Нет доступа к БД** | Converter-validator не читает и не пишет в БД. Все данные получает через тело запроса | А–Ж | `converter_validator_service_api.md` |
| **Preview vs Full** | Preview — быстрые метаданные без LLM и валидации; Full — полный цикл | А, Д | `converter_validator_service_api.md` |
| **LLM — опционально** | LLM включается параметром `use_llm`. Без LLM — эвристики | А, Б, Г, Е | `app_settings.llm` |
| **Бизнес-ключ на основе метаданных** | `title_hash_sha256` вычисляется по нормализованным метаданным, а не по содержимому файла | А, Б, Е | `normalizer_specification.md` §2 |
| **Маппинг типов через CV** | Converter-validator отвечает за преобразование типов блоков OCR/Parser → Registry | А, Б | `pipeline1-formation_detail.md` |
| **Кросс-ссылки извлекаются на шаге 9** | Ссылки на другие документы извлекаются после построения иерархии, перед отдачей результата | А, Б | `normalizer_specification.md` §8 |
| **Обнаружение аватаров → manual** | Латинские аватары в названии переводят `decision` в `manual` | Е | `normalizer_specification.md` §3.3 |
