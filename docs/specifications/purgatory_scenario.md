# Сценарии использования: загрузка и дедупликация документов

> Описание типовых сценариев работы с реестром документов — от загрузки файла до создания логической карточки.

---

## Сценарий А: Загрузка нового файла (автоматическое создание)

**Контекст:** Инженер загружает сканированный PDF ГОСТ 20868-81 «Стойки...» через Web UI.

**Поток:**

1. **Загрузка файла:** POST /drafts → файл попадает в MinIO, создаётся черновик (`registry.drafts`) и задача (`pipeline.tasks`).
2. **Preview-фаза:** OCR/Parser распознаёт первые 3 страницы → Converter-validator извлекает метаданные:
   - `doc_code`: `20868-81`
   - `title`: `"Стойки..."` (нормализованное название для бизнес-ключа)
   - `source_type`: `GOST`
   - `era`: `USSR` (определяется по году `1981`)
   - `mks_oks_code`: обнаруживается на первой странице (например, `47.020`)
3. **Проверка уникальности:** `POST /registry/documents/check-uniqueness` — бизнес-ключ `title_hash_sha256` не найден в БД → документ уникален.
4. **Решение пользователя:** Preview показывает метаданные → инженер нажимает «Утвердить» (`approve`).
5. **Full-фаза:** Полный проход OCR/Parser + Converter-validator по всем страницам.
6. **Создание карточки:** Registry создаёт запись в `registry.documents`:
   - `doc_code`: `20868-81`
   - `title`: `"Стойки..."` (исходное название)
   - `title_hash_sha256`: SHA-256(`USSR|gost|47.020||20868-81|стойки...`)
   - Параллельная классификация: `mks_oks_code = '47.020'`, `okstu_code = NULL`
   - `source_type`: `GOST`, `era`: `USSR`, `validity_status`: `active`
   - `classification_status.mks_status`: `CONFIRMED` (код найден в справочнике)
7. **Создание версии:** `registry.document_versions` — файл с `file_hash_sha256` по CAS-пути.
8. **Индексация:** RAG Builder забирает документ со статусом `created` → чанкинг → эмбеддинги → pgvector.

**Результат:** Документ доступен в поиске. Одна логическая карточка → один файл.

## Сценарий Б: Ввод из реестра (без файла)

**Контекст:** Администратор вносит в систему нормативный документ, которого ещё нет в электронном виде (известно только название и номер).

**Поток:**

1. **Создание карточки** (без файла): вызов `POST /registry/documents` напрямую (минуя черновик) через API Registry.
2. **Поля:**
   - `doc_code`: `"РД 5.1234-90"`
   - `title`: `"Руководящий документ..."` (может быть уточнён позже)
   - `title_hash_sha256`: вычисляется сразу (по `doc_code` + `title` + `era`)
   - `source_type`: `RD`
   - `era`: `USSR`
   - `validity_status`: `active`
   - `mks_oks_code`: `47.020` (известен администратору)
   - `classification_status.mks_status`: `CONFIRMED`
3. **Статус:** `created` — карточка создана, но файла нет.
4. **Позже, когда файл найден:**
   - Загрузка через стандартный POST /drafts
   - Парсинг извлекает `doc_code` и `title`
   - Проверка уникальности находит существующую карточку по `title_hash_sha256`
   - Вместо создания новой карточки — привязка версии файла к существующей
   - Статус черновика переводится в `approved` (автоматически, т.к. документ уже известен системе)

**Результат:** Администратор может предварительно регистрировать документы, не дожидаясь получения файлов. При появлении файла он автоматически привязывается к существующей карточке.

**Важно:** Бизнес-ключ должен вычисляться по нормализованному названию, а не по файлу. Только тогда будет найдена существующая карточка.

## Сценарий В: Разные форматы одного ГОСТа

**Контекст:** В системе уже есть ГОСТ 2.105-95 в виде сканированного PDF. Позже поступает цифровая DOCX-версия того же стандарта, выпущенная с другим издательским оформлением.

**Поток:**

1. **Загрузка первого файла** (PDF, скан):
   - Создаётся карточка документа в `registry.documents`
   - Версия #1: `registry.document_versions` с `file_hash_sha256` = хэш PDF
   - `title_hash_sha256`: `SHA-256(RF|gost_r||ГОСТ 2.105-95...)`

2. **Загрузка второго файла** (DOCX, цифра), спустя время:
   - POST /drafts → Preview → парсинг извлекает `doc_code = "2.105-95"` и `title = "ГОСТ 2.105-95 ЕСКД..."` 
   - Проверка уникальности: `title_hash_sha256` **совпадает** с существующей карточкой
   - **Система НЕ создаёт новую карточку** — вместо этого:
     - Черновик завершается с привязкой к существующему документу
     - Создаётся **новая версия**: `document_versions.document_id` → существующий `documents.id`
     - `version_number = 2`
     - `file_hash_sha256` = хэш DOCX (отличается от хэша PDF → UNIQUE не нарушен)
   - Статус документа остаётся `created` (переиндексация запускается отдельно)

**Результат:** Один логический документ (одна карточка в `registry.documents`) с двумя версиями файла (PDF-скан и DOCX-цифра). 

**Связь между версиями:**
```json
registry.documents {
    id: 42,
    title: "ГОСТ 2.105-95 ЕСКД...",
    title_hash_sha256: "abc123...",
    current_version_id: 2  // последняя загруженная версия
}

registry.document_versions [
    { id: 1, document_id: 42, version_number: 1, 
      file_hash_sha256: "e3b0c44...",  // PDF
      file_path: "42/v1/e3b0c44..." },
    { id: 2, document_id: 42, version_number: 2, 
      file_hash_sha256: "a7ffc6f...",  // DOCX
      file_path: "42/v2/a7ffc6f..." }
]
```

## Сценарий Г: Обработка дубликата (коллизия бизнес-ключа)

**Контекст:** Пользователь пытается загрузить ГОСТ 12345-77 (СССР), который уже есть в системе.

**Поток:**

1. **Загрузка файла:** POST /drafts → Preview → извлечение метаданных.
2. **Проверка уникальности:** `POST /registry/documents/check-uniqueness`
   - `title_hash_sha256`: уже существует
   - `file_hash_sha256`: отличается (другой файл)
3. **Результат:** `is_duplicate = true`, `candidates` — список совпадений с `similarity`.
4. **UI:** Показывает: «Документ с таким названием уже существует (ГОСТ 12345-77, ID 42)». Предлагает привязать файл как новую версию или отменить.
5. **Если пользователь подтверждает:** как в Сценарии В — создаётся новая версия.
6. **Если пользователь отклоняет:** черновик переводится в `discarded` с комментарием `DUPLICATE_REJECTED`.

## Сценарий Д: Foreign-документ (DNV, ISO)

**Контекст:** Загружаются «DNV Rules for Classification of Ships» (Норвегия).

**Поток:**

1. **Определение типа:** Парсер распознаёт `DNV-RU-SHIP-Pt3` → `source_type = DNV`
   - `is_foreign = true` → упрощённая нормализация (без детекта аватаров)
2. **Классификация:** `mks_oks_code = 47.020` (Конструкция корпуса)
   - `okstu_code = NULL` (ОКСТУ не применяется для иностранных документов)
   - `classification_status.okstu_status = NOT_USED`
3. **Эра и юрисдикция:**
   - `era = CURRENT`
   - `jurisdiction = NO` (Норвегия)
   - `issuing_body = DNV GL`
4. **Бизнес-ключ:**
   ```
   SHA-256(CURRENT||47.020||dnv|dnv-ru-ship-pt3|нормализованное название)
   ```
5. **Хранение:** CAS-путь формируется по общему правилу, `safe_filename` сохраняет английское имя.

## Сценарий Е: Пустой документ (0 страниц)

**Контекст:** Загружен PDF, который оказался пустым (0 страниц) или нечитаемым для OCR.

**Поток:**

1. **Preview-фаза:** OCR/Parser возвращает 0 страниц.
2. **Автоматическое отклонение:** Черновик переводится в `discarded` с кодом `EMPTY_DOCUMENT`.
3. **UI:** Показывает сообщение: «Документ пуст (0 страниц). Загрузите другой файл».
4. **Карточка документа** в `registry.documents` не создаётся.
5. **Очистка:** Файл остаётся в MinIO (для анализа), но запись черновика помечается как ошибочная.

## Ключевые принципы (из сценариев)

| Принцип | Сценарии | Описание |
|---------|----------|----------|
| **Логический корень** | А, Б, В | Один документ (ГОСТ) = одна карточка в `registry.documents`, независимо от числа файлов |
| **Дедупликация по бизнес-ключу** | А, Б, В, Г | `title_hash_sha256 = SHA-256(era \| source_type \| mks_oks_code \| okstu_code \| doc_code \| normalized_title)` |
| **CAS-дедупликация файлов** | В, Г | `file_hash_sha256` UNIQUE — один и тот же файл не может быть загружен дважды |
| **Файл опционален** | Б | Карточка может существовать без файла. Файл добавляется позже как новая версия |
| **Иностранные документы** | Д | Упрощённая нормализация, `okstu_status = NOT_USED`, своя юрисдикция |
| **Пустой документ** | Е | Автоматическое отклонение на preview-фазе, карточка не создаётся |
